## 零、总体架构决策（先定这个，后面才不返工）

### 0.1 不做的事：不搭四智能体并行图

需求文档附录 B 记录了 24 条样本的三组对照实测。核心结论：

| 方案 | 精确率 | 词元（提示/生成） | 单条耗时 | 报告条数 |
|---|---|---|---|---|
| 单次综合审查（四维度合在一個提示词） | 0.933 | 5204 / 2159 | 1.68 秒 | 20 |
| 四个审查员并行 | 0.778 | 10712 / 5261 | 2.12 秒 | 63 |
| 单次综合 + 规则原文注入 | **1.000** | 9308 / 2563 | 1.75 秒 | 17 |

**四个审查员并行没有任何召回收益（三组召回率均为 1.000），精确率反而下降 0.155，成本翻倍。** 因此不采用。

### 0.2 要做的事：一个审查智能体 + 按文段并行 + 确定性仲裁

```
                  ┌─────────────────────────────────────────┐
   输入文案 ──────▶│ 1. 切句 + 词库前置扫描（1 毫秒级）        │
                  └───────────────┬─────────────────────────┘
                                  ▼
                  ┌─────────────────────────────────────────┐
                  │ 2. 分片（每片 ≤4 句），并发 4 路           │
                  │    每片：检索规则条文 → 单次审查调用       │
                  │    （一次调用内按 4 个维度分别输出）       │
                  └───────────────┬─────────────────────────┘
                                  ▼
                  ┌─────────────────────────────────────────┐
                  │ 3. 确定性仲裁：合并/取最高/无依据降级      │
                  │    （纯代码，无模型调用，毫秒级）          │
                  └───────────────┬─────────────────────────┘
                                  ▼
                  ┌─────────────────────────────────────────┐
                  │ 4. 落库 + 返回结构化清单                   │
                  └─────────────────────────────────────────┘
```

实测支撑：360 字文案，整篇单次 8.38 秒 → 按文段四路并行 5.43 秒（快 35%）；"四审查员并行 + 模型仲裁"端到端 25.13 秒，其中模型仲裁占 11.15 秒（44%），改为确定性仲裁可省掉这 11 秒。

### 0.3 与现有系统的挂载方式（不改主图）

现有对话主图（`src/agent_graph.py` 第 186-195 行）是：`START → agent`，`agent` 条件边到 `tools` 或 `END`，`tools` 无条件回边到 `agent`。共 4 节点 4 边。

**挂载方案：把审查能力包成一个工具，追加到 `bind_tools` 列表与 `ToolNode` 列表。**

已实测验证（脚本 `tmp/demo_mount3.py`，临时文件已删除）：把编译好的审查子图包进一个 `@tool` 函数，追加到工具列表后，工具总数从 19 变 20，主图节点仍是 4 个、边仍是 4 条，**拓扑零改动**。

```python
@tool
def compliance_review(text: str, platform: str = "", category: str = "",
                      brand_name: str = "", product_attr: str = "") -> str:
    """内容合规预审：对文案做逐句合规检查（广告法/平台规则/类目/品牌四个维度）。
    返回定位到句的问题清单，含原文句子、问题类型、违反依据原文、严重度、修改建议。"""
    ...  # 内部调 ComplianceService，跑编译好的审查子图
```

改动量：`agent_graph.py` 只需 2 行（`_build()` 里的 `all_tools` 加一项、`__init__` 里的 `bind_tools` 加一项），加上 import 1 行。**共 3 行。**

**注意事项（实测踩过）**：
- 工具描述会让 `bind_tools` 的 schema 变大。当前 19 个工具的完整 schema 是 10920 字节，仅名称+描述是 6359 字节。新增一个工具约 +200 字节，描述必须控制在 3 行以内，否则会加剧模型选工具的负担（现有源码注释已记录"只 bind 基座会让模型对 M4/M5 工具盲调"这个问题）。
- 不要把审查子图直接 `add_node` 挂到主图。实测：子图状态字段比父图多时直接挂载不报错，但父图拿不到子图独有字段（数据静默丢失）。走工具封装可以避免这个问题。

### 3.2 审查子图（`src/server/compliance_graph.py`）

按实测结论，并行的单位是文段。子图结构：

```python
"""审查子图：切句 → 分片 → 四路并行审查 → 汇总。

实测要点（务必遵守，否则会踩坑）：
1. Send 的负载字段必须在子图状态类型中显式声明，否则被静默丢弃（报 KeyError）。
2. 子图与父图不得有同名的可变累加字段，否则并行分支同一步写同一通道抛
   InvalidUpdateError: Can receive only one value per step。
   本文件用 in_text 而非 text 就是为了避开这个。
"""
from typing import Annotated, TypedDict
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send

class ChunkState(TypedDict):
    """单片审查的状态。字段名与父图区分。"""
    seg_id: str
    seg_text: str
    platform: str
    category: str
    brand_name: str
    product_attr: str
    findings: Annotated[list, operator.add]

class ReviewState(TypedDict):
    """整篇审查的状态。"""
    raw_text: str
    platform: str
    category: str
    brand_name: str
    product_attr: str
    segments: list[str]
    findings: Annotated[list, operator.add]

def plan_segments(state: ReviewState) -> dict:
    """切句（中文句号/问号/感叹号/换行），按 ≤4 句一片聚合。
    实测：360 字切出 14 句，按 4 句一片得 4 片。"""
    ...

def fan_out(state: ReviewState) -> list[Send]:
    """并行分发。每片一个 Send。"""
    return [Send("review_segment", {
        "seg_id": f"S{i}", "seg_text": seg, "platform": state["platform"],
        "category": state["category"], "brand_name": state["brand_name"],
        "product_attr": state["product_attr"], "findings": [],
    }) for i, seg in enumerate(state["segments"])]

def review_segment(state: ChunkState) -> dict:
    """单片审查：先检索该片相关的规则条文，再一次性审查四维度。"""
    rules = RuleRetriever().retrieve(state["seg_text"], state["platform"], state["category"])
    result = llm_call_four_dimensions(state["seg_text"], rules, ...)
    return {"findings": result}

def aggregate(state: ReviewState) -> dict:
    """汇总不做判定，只做收集。仲裁在子图外由确定性代码完成。"""
    return {}

# ---- 构图
seg = StateGraph(ChunkState)
seg.add_node("review_segment", review_segment)
seg.add_edge(START, "review_segment")
seg.add_edge("review_segment", END)
seg_graph = seg.compile()

g = StateGraph(ReviewState)
g.add_node("plan", plan_segments)
g.add_node("review_segment", seg_graph)      # 已编译子图挂成节点（实测可用）
g.add_node("aggregate", aggregate)
g.add_edge(START, "plan")
g.add_conditional_edges("plan", fan_out, ["review_segment"])
g.add_edge("review_segment", "aggregate")
g.add_edge("aggregate", END)
COMPLIANCE_GRAPH = g.compile()
```

**并发控制**：`Send` 的分发数量等于片数。360 字 4 片没问题，2000 字可能 15 片。必须在 `plan_segments` 里做上限截断，超过 8 片则合并成 8 片（每片句数增加）。理由：实测外部接口并发 24 路无失败，但那是最小请求；长请求下的限流阈值未实测，保守取 4-8。

| 功效宣称 | 0 | 0 |
| 绝对承诺 | 0 | 0 |
| 医疗用语 | 0 | 0 |

**2 处命中还都是达人昵称**（"王者顶级工作室""撒娇男人最好命"），不是文案违规。

而且这 1703 块语料的形态是"商单台账"——记录的是预算、千次曝光成本、达人组合、结案数据，**根本没有成篇的内容文案**。全库含"脚本"的块有 16 个，但那 16 个块里"脚本"两个字出现在复盘结论中（"档期偏紧导致脚本打磨时间不足"），不是脚本正文。含"口播"的 62 块同理。

| 否定语境误报率 | 含否定/免责的合规句被误报的比例 | ≤ 0.05 | 词库基线 0.500，必须靠过滤压到 0.05 |
| 合规文案平均误报条数（每 300 字） | | ≤ 1 条"高" + ≤ 3 条"中" | |
| 严重度判定一致率 | 报出条目的严重度与标注一致的比例 | ≥ 0.75 | 严重度是主观判断，不要求太高 |

**目标值的依据说明**：召回率 0.90 与精确率 0.85 不是行业标准，而是按"用户能忍受的程度"定的——如果 10 条违规漏 1 条，用户会觉得有用；如果报 10 条有 2 条是假的，用户会开始怀疑全部结论。**这些值是产品判断，不是技术测量结果，应在第四阶段结束后根据真实使用数据调整。**

### 5.3 评测脚本

`scripts/eval_compliance.py`（参照现有 `data/eval` 与 `reports/` 下的评测实践）：

```python
"""合规审查评测：跑全量评测集，输出各指标与分类型明细。

用法：PYTHONPATH=src .venv/Scripts/python.exe scripts/eval_compliance.py \
        --gold data/eval/compliance_gold.jsonl --out reports/compliance_eval.json
"""
```

输出必须包含：
1. 总体指标表
2. 按问题类型（11 类）的召回率与精确率明细——**这是定位弱项的唯一手段**
3. 按维度（4 个）的明细
4. 按品类（4 个）的明细
5. 全部漏报与误报的明细列表，含原文句子——人工复核用

### 5.4 误报闭环

**`compliance_false_positive` 表的使用流程**：

1. 用户在问题条目上点"这是误报"→ 填理由 → 落库（`verdict` 为空）。
2. 合规负责人每周审一次待处理的申诉。
3. 裁决为"确认误报"的，按 `fix_action` 分三种处置：
   - `加白名单`：把该句加入 `compliance_rule` 的例外清单（新增字段或新建例外表）
   - `调规则`：修改规则条文的 `plain_text` 或 `examples`
   - `改词库`：把该词条的 `negation_sensitive` 置真，或加例外上下文
4. 裁决为"非误报"的，记录理由，用于回复用户。

**这个闭环的指标**：误报申诉率（申诉数 / 报出总条数）。目标 ≤ 5%。**这个数字必须持续监控，它是这个功能能否活下来的唯一指标。**

### 5.5 第四阶段验收

| 断言 | 判据 |
|---|---|
| 评测集规模 | ≥ 250 条，其中违规 ≥ 150 条 |
| 评测集双人标注 | 每条有至少 2 个标注来源，一致率 ≥ 0.80 |
| 全部指标达标 | 5.2 节的 10 项指标全部达到目标值 |
| 评测脚本可复现 | 同一评测集连跑两次，指标差异 ≤ 0.02（模型温度已设为 0，但仍可能有波动） |
| 误报申诉可走通 | 申诉 → 裁决 → 处置 → 复查，全链路可执行 |

## 六、风险清单与应对

### 6.1 高风险（必须解决，否则功能不成立）

**风险一：规则知识库建不起来，依据全是编的**

- 现状：规则语料 18 块 2701 字，八项主题覆盖矩阵里六项全平台缺失。
- 实测证据：依据可追溯率 36.8%（19 条里只有 7 条能在注入的规则原文找到出处）。
- 影响：用户看到"依据：《广告法》第九条"会相信它，但条文内容可能是模型编的。**这比不给依据更危险。**
- 应对：
  1. 第一阶段先建库，规则条数不达标（<150 条）不上线语义审查。
  2. 代码层强校验 `_verify_basis`，不通过的降级为"提示"并从违规计数排除。
  3. 界面层对"提示"级条目用明显的弱化样式，并与"违规"视觉区隔。
  4. 每个规则条目必须填 `source_file` 与 `article`，前端提供"查看依据原文"的跳转。
- **残余风险**：即便做完上述四条，依据可追溯率能到多少仍未知。这是本计划最大的不确定性。

**风险二：误报率高导致用户不信任**

- 实测证据：四审查员并行方案精确率 0.778（24 条样本中 4 条误报）；确定性词库精确率 0.500（16 条样本中 4 条误报，全部来自否定语境）。
- 影响：用户用两次就发现"它老报错"，第三次就不看了。**这是这类功能最常见的死法。**
- 应对：
  1. 词库必须过否定语境过滤，未过滤前不上线（第一阶段门槛）。
  2. "高"级条目精确率单列指标，标准 ≥0.92，比整体精确率更严。
  3. 每条问题必须能点开看到依据原文，让用户自己判断。
  4. 误报申诉必须能在两次点击内完成，申诉结果必须反馈给用户（"已记录，将在规则更新中处理"）。
  5. **首版只上线"高"级与"中"级条目，"低"与"提示"默认折叠。** 宁可少报，不可多报错。
- 可监控指标：误报申诉率 ≤5%。

**风险三：多智能体调试复杂度**

- 实测证据：并行分发有两个隐蔽的坑（Send 负载字段被静默丢弃报 KeyError；子图与父图同名可变字段抛 `InvalidUpdateError: Can receive only one value per step`）。第一个坑的表象（键不存在）与根因（字段未在状态类型声明）距离很远，排查成本高。
- 影响：调试时间不可控。
- 应对：
  1. **架构上已经把智能体数量降到 1 个**（需求文档附录 B 的实测结论：四个审查员并行无召回收益、精确率反降）。这是最有效的应对——问题从"多智能体协调"降级为"单智能体 + 并行分片"，协调逻辑简单一个数量级。
  2. 并行结构照抄已验证的最小可行示例（本文档 3.2 节），字段命名规则写死：子图状态字段一律加前缀（`in_text`、`seg_text`），永不与父图同名。
  3. 单个 `Send` 分支的失败必须被捕获，不能让一个分片失败拖垮整次审查（现有 `ToolNode` 已有 `handle_tool_errors` 的先例）。
  4. 每个分片的审查结果落中间表，便于单独复现某一片的判断过程。

### 6.2 中风险

**风险四：并行调用的成本与限流**

- 实测证据：并发 4/8/12/16/24 路全部成功，无限流（但都是最小请求 `max_tokens=8`）。长请求下的阈值未实测。
- 应对：
  1. 并发上限硬编码为 4，配置可调，超限排队。
  2. 分片数上限 8 片（2000 字以上合并分片）。
  3. 单次审查词元预算 2500（提示+生成），超预算则降级为"仅词库"。
  4. 相同文案做内容哈希，24 小时内复用结果。
  5. 失败重试 2 次，仍失败则该片标记"未完成"，返回部分结果并明确标注。

**风险五：长文案延迟不可控**

- 实测证据：360 字整篇单次 8.38 秒、切分并行 5.43 秒。500-2000 字**未实测**。
- 应对：
  1. 按 500 字为一档设延迟预算，超预算先返回部分结果。
  2. 前端必须有进度提示（实测 5.43 秒无进度已经是煎熬）。
  3. 对超长文案（>2000 字）建议用户分段提交，界面提示"建议按段落提交，结果更准更快"。

**风险六：平台规则时效性**

- 三个平台的社区规范是动态文档，人工抄录必然滞后。
- 应对：
  1. 规则库每条带 `version` 与 `effective_from`，界面显示"规则库版本：某年某月某日"。
  2. 每次审查记录版本快照，历史结果可复现。
  3. 建立月度复核机制（合规负责人每季度至少复核一次），**本期不做自动更新**。
  4. 界面上明确写"审查结果基于本地规则库，不保证与平台实时一致"。

**风险七：改 SYSTEM_PROMPT 破坏现有对话能力**

- 现有提示词已约 60 行，且源码注释记录了工具绑定的服从性问题。
- 应对：
  1. 加一行工具说明，不加第二行。
  2. 加完后必须跑现有对话回归（R4/R5 断言）。
  3. 如果回归失败，改为不挂工具、只做独立页面（对话入口降级为非必需）。

### 6.3 低风险

**风险八：前端长文案渲染卡顿** — 已通过区间二分定位规避（4.3 节的性能断言）。

**风险九：评测集标注噪声** — 双人标注 + 第三人裁决，一致率 ≥0.80 为门槛。

**风险十：审查记录表膨胀** — 每次审查 1 行主表 + N 行明细。按每天 50 次、每次 10 条估算，年增约 18 万行，PostgreSQL 无压力。
