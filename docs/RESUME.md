## 二、面试问答准备

### Q1：为什么用 LangGraph 而不是 LangChain 的 Chain？

Chain 是线性数据流，而这个业务需要**多步决策 + 人工介入 + 可中断恢复**：

- `router` 节点做意图分流，三条业务路径（构思/速查/跟进）走不同子图
- 构思路径需在「生成方案后」暂停等运营确认，`interrupt()` 原生支持，Chain 得自己造轮子
- 运营提出修改后要**回到同一节点重生成**，形成带条件边的循环（上限 3 轮防死循环）
- Checkpointer 持久化状态，支持跨进程恢复

### Q2：混合检索为什么有效？RRF 原理？

关键词检索（BM25）和向量检索互补：前者擅长**精确术语匹配**（如「星图」「刊例」「DC20260081」这类专有名词和编号），
后者擅长**语义泛化**（「报价」↔「刊例」↔「价格」）。

RRF（Reciprocal Rank Fusion）用 `score = Σ 1/(k + rank)` 融合多路排名，**只看名次不看原始分数**，
所以不需要对不同检索器的分数量纲做归一化调参 —— 这是它被广泛采用的原因。

### Q3：Reranker 和向量检索什么区别？为什么要两级？

| | 向量召回（双塔 Bi-Encoder） | 重排（Cross-Encoder） |
|---|---|---|
| 结构 | query 和 doc 分别编码后算余弦 | query+doc 拼接后整体过模型 |
| 精度 | 较低（交互信息缺失） | 高（有 token 级交互） |
| 速度 | 快，可预计算索引 | 慢，每个候选都要前向一次 |
| 角色 | 粗排，从海量里取 Top-N | 精排，对 N 个候选细排 |

**级联**兼顾效率与精度：先用向量从 457 块里粗取 30 条候选，再用 reranker 精排到 5 条。

实测数据支撑这个设计：本地 CrossEncoder 在 CPU 上 **1126ms/条**（30 条候选要 33.8 秒），
全量排序不现实，所以必须两级。换用云端 `gte-rerank-v2` 后降到 **35ms/条**。

**追问：候选数为什么定 30 又裁到 10？**
实测发现 ground-truth 文档在重排前候选池 top-5 内命中率已达 **54/54 = 100%**，
说明再往下的候选对最终 Top-K 没有贡献。于是把送入 reranker 的候选数从 30 裁到 10
（新增 `rerank_cand_k` 参数，不动召回池宽度），**耗时 -16.6% 而 MRR/Recall@5 反而微升**
（0.880→0.883 / 0.981→0.986）。这是「先量测再优化」而非凭感觉调参的结果。

### Q4：如何解决幻觉？

三层防线：

1. **溯源层**：检索结果强制携带元数据（来源文件、章节、年份），由代码确定性渲染「参考来源」区块
   （注：**未实现分数阈值过滤**，凡进入 context 的片段都会注入）
2. **提示层**：System Prompt 显式授权「不知道」，要求数值字段必须原样引用、禁止估算；
   `<context>` 标签隔离检索内容与指令
3. **校验层**：`validate_citations()` 检测引用编号是否越界；「参考来源」区块由**代码确定性渲染**，
   不依赖模型自觉输出

实测效果：问「我们和腾讯签的年度框架合同金额是多少」，模型回答「知识库中未找到相关依据」并说明缺失内容，**零引用、未编造数字**。

### Q5：切分策略怎么定的？为什么用父子块？

- **按标题层级语义切分**优先，保证块内语义完整
- 兜底 512 token 窗口 + 15% 重叠，防跨块语义断裂
- 表格转 Markdown **整块保留**，不跨块切断（否则表头与数据行分离，检索到也没用）
- **父子块**：子块（≈560 字）用于检索，精度高；父块（整节）用于生成，上下文完整。
  命中子块后回查父块喂给 LLM，兼顾检索精度与生成质量

### Q6：怎么评估效果？（**重点，体现工程严谨性**）

自建 **54 条**带 ground-truth 标签的评测集，覆盖 6 类问题、3 个难度。关键设计是
**评测集从真实台账反向生成**（如取一条真实结案单，问「这个商单的 ROI 多少」，正确答案就是该商单文档），
所以标签是**客观的、可复现的**，不是人工拍脑袋标注。

指标用 Hit@k / Recall@k / MRR，并做**消融实验**逐组件验证贡献。结果是**非单调**的：
BM25 单路融合会引入同构文档干扰，需配合文档级去重与文档类型先验才能转正 —— 这比"每项都提升"更真实。

### Q7：Human-in-the-Loop 怎么实现的？

`human_review` 节点调用 LangGraph 的 `interrupt()` 挂起图执行，把方案抛给前端；
运营在 Streamlit 面板上选「确认通过」或「提出修改」，通过 `Command(resume=...)` 恢复。
修改意见作为 `human_feedback` 写入 state，`revise` 节点带着意见重新生成后**回到 human_review 再次中断**，
`revision_count` 上限 3 轮。Checkpointer 负责全程状态持久化。

### Q8：数据是怎么构造的？为什么不用公开数据集？

MCN 商单数据涉及商业机密，公开渠道拿不到。做法是：

- **平台规则/方法论**：爬取巨量星图公开规则 + 行业报告，改写为内部 SOP 文档
- **结构化台账**：基于真实业务逻辑程序化生成（达人 120 / 商单 90 / 跟进 173），
  并做了数据一致性校验（ROI 中位数 1.09、CPM 25–60 元，落在行业区间）
- **关键设计**：104 篇语料**由结构化数据渲染生成**，所以文档与台账天然对得上，
  引用溯源可以真正验证，不会出现"文档说有、库里没有"的假数据

### Q9：你是如何定位那个「同构文档淹没」问题的？

现象：刊例类问题的 Hit@5 只有 0.400。

排查：打印向量召回和 BM25 召回的**各路排名**，发现美妆刊例表在向量路排第 1，
但诊断 RRF 后的排名时发现它掉到第 15。

根因：45 份同构的在途跟踪单（结构、字段高度相似）在两路召回里都大量上榜，
RRF 把两路的 `1/(k+rank)` 累加，数量优势直接盖过了单篇高相关文档。

修复：融合前按 `doc_id` 去重（每文档最多 2 块），让"文档多样性"参与竞争。

### Q10：Rerank 为什么最终走了云端 API？为什么 Embedding 用本地？

**Rerank 的选型是实测出来的，不是拍脑袋的**，三个阶段：

1. **本地优先**：Ollama 无 rerank 能力（`/api/rerank` 返回 404、官方库无 CrossEncoder 模型、
   bert 后端不暴露打分接口），所以用 sentence-transformers 加载 `bge-reranker-v2-m3`。
   但实测 **CPU 上 1126ms/条**，一次 54 题消融要 60+ 分钟。
2. **尝试 GPU 加速，实测失败**：本机 GTX 1650 Ti 只有 4GB 显存，
   实测启动前可用显存仅 free 1.16G / 4.00G（不足以承载 fp32 权重，未跑通）；
   换 fp16 后加载阶段显存被吃满（free 2.35G → 0.00G），
   推理时权重在显存与宿主内存间反复搬运，**反而慢到 3225ms/条（比 CPU 还慢 3 倍）**。
   根因是桌面与系统组件已占用约 2.84G（4.00G − free 1.16G），属硬件限制而非配置问题。
3. **改走云端**：阿里云 DashScope `gte-rerank-v2`，**35ms/条（32× 提升）**，
   消融总耗时 177 秒；而且质量更好（Hit@1 0.741→0.778），还移除了 3.9GB 的 torch 依赖。

**这个决策过程本身是加分项**：拿数据否掉一个看似「更专业」的方案，比盲目堆硬件更有价值。

Embedding 保留本地则是**先验证再切换**：对比了本地 bge-m3 与原云端方案的向量统计量
（标准差均为 0.03124）、跨模型余弦相似度（0.9205，提示同源）、语义区分度
（本地 0.2838 vs 云端 0.2753），确认无损后才重建全部 457 条索引 —— 且 Embedding 是批量
离线调用、延迟不敏感，本地零成本更划算；而 Rerank 在查询链路上、延迟敏感，走云端更合适。

## 四、诚实声明（面试被追问时要用）

- 项目为**个人作品**，数据为仿真构造，不含真实客户信息
- 评测集 54 条规模偏小，结论用于**组件对比**而非绝对效果承诺
- Milvus 用 `MemorySaver` 级别的 checkpoint（内存态），生产应换 PostgreSQL/SQLite Checkpointer
- Rerank 目前走 DashScope 云端 API：本地栈实测更慢（CPU 1126ms/条、GPU fp16 3225ms/条），
  若需完全离线需改 ONNX Runtime（预期 CPU 上 2-4 倍加速），这是已知的改进方向
- 消融⑧组的 ΔMRR（+0.003）与 ΔRecall@5（+0.005）幅度很小，**不宜声称显著提升**，
  该组的价值在「耗时降 16.6% 而精度不降」，属性能优化而非效果优化
