### 写法 A（技术栈优先，适合投递大模型应用开发岗）

- **RAGAS 四指标评测**（检索层+生成层）：抽样 20 条真实查询走完整 RAG 链路，**faithfulness（忠实度）0.959（近零幻觉）**、answer_relevancy 0.794、context_precision 0.705、context_recall 0.559；低分项逐条归因（列表型回答 Embedding 相似度天然偏低/聚合型问题对齐损耗），非幻觉问题
- **结构化/非结构化双路检索设计**：14289 达人 + 400 商单走 **SQL 精查**（类目/量级/粉丝/报价/排他期过滤，`search_kols` 毫秒级），非结构化语料（案例/刊例/方法论/跟踪单 2063 块）走向量检索——由 LLM 在对话中自主决定查哪一路

- **商单字段变更审批流**：对话内 Agent 无权限直改主字段 → `request_deal_change` 工具建申请（自动捕获旧值）→ 审批中心批准/驳回 → 批准自动写回 + 跟进流水留痕；一商单可挂多审批
- **图片识图沉淀闭环**：微信谈判截图拖入对话 → qwen-vl 完整转写（实测主模型 deepseek-v4-flash 对 `image_url` 静默丢弃，视觉必须独立通道）→ Agent 从转写抽合作特质（附原文引用）→ 确认卡入库、原图 MinIO 留档可回溯——经验从「截图里的死数据」变成「可检索的知识库资产」
- **导入三通道 + Agent/管理员双审**：达人库/商单台账/非结构化文档统一入暂存区，Agent LLM 质检（异常值/缺字段/脱敏检查，实测抓出预算 -20000 脏数据判 reject）→ 管理员确认/驳回后才落正式表；非结构化文档确认后秒级向量化、即时可检索——所有外部数据入口都有 AI 预审 + 人工把关双重防线

## 二、面试问答准备

### Q1：为什么用 LangGraph 而不是 LangChain 的 Chain？bind_tools 和固定流水线的区别？

Chain 是线性数据流；v1 的 router 是「三元分类 + 固定路径」，用户一句「顺便记个跟进」它就处理不了。
真 Agent 的本质区别：**工具选择的决策权交给 LLM**——`bind_tools` 把 19 个工具的签名+docstring 给模型，
模型输出 tool_calls，ToolNode 执行后结果回喂，循环直到模型不再调工具。
业务价值：一次对话里可以自然完成「查达人 → 出方案 → 记跟进 → 提审批」的混合意图，不用穷举路由分支。

### Q2：结构化查询和向量检索为什么分两路？怎么决定走哪路？

达人/商单筛选是**精确过滤问题**（类目=美妆 AND 粉丝>10w AND 报价<5w），SQL 是唯一正解——
向量检索在这类查询上既慢又不准。而「我们做过哪些母婴成功案例」是**语义召回问题**，SQL 写不出来。

决策交给 LLM：工具 docstring 写清「何时该调我」（search_kols vs search_knowledge），
模型按用户问题自主路由。这是 Agent 相对固定 pipeline 的又一优势——**路由本身也是涌现的**。

### Q3：为什么要重跑消融？现在的指标怎么理解？

**评测集和语料必须同源**，否则指标无效。语料重建为真实业务数据后（2063 块，4.7×），
评测集同步从库反向重建为 98 条——检索空间更大、同构干扰更多，题目难度实质上升。
价值看**相对增益**：完整链路相对基线 Hit@1 +0.143 / MRR +0.126，8 组消融每一组的贡献都可拆解验证。
指标口径：Hit@1 0.694 / MRR 0.788（语料 2063 块、评测集 98 条、动态反查生成）——
引用指标时带口径是基本功，不同语料/评测集之间的绝对值没有可比性。

### Q4：RAGAS 都评了什么？faithfulness 0.959 说明什么、不说明什么？

评了两层：**检索层** context_precision（0.705）/ context_recall（0.559）+ **生成层** faithfulness
（回答是否都能从检索 context 推出，0.959 ≈ 近零幻觉）和 answer_relevancy（0.794）。

faithfulness 0.959 说明**生成层几乎不编造**——这靠的是「数值强制引用 + 无依据明确拒答 + 引用越界校验」三道防线，
是结构保证不是模型自觉。但它**不说明回答准**——relevancy 0.794 的低分样本是「列出符合条件达人」类查询，
回答是短列表，Embedding 相似度天然偏低。**诚实结论：近零幻觉成立，相关性合格但有优化空间。**

### Q5：怎么解决幻觉？

四层防线：

1. **检索层**：混合召回 + rerank，context 质量是前提
2. **提示层**：数值必须原样引用、context 没有就明确说「未找到依据」、`<context>` 标签隔离
3. **校验层**：`validate_citations()` 引用越界检测，「参考来源」由代码确定性渲染
4. **评测层**：RAGAS faithfulness 实测 0.959 背书，不靠口头承诺

### Q6：14 张表怎么设计的？为什么 Service 层唯一写库？

v1 的 6 张（达人/商单/品牌/跟进/chunk 父子）+ v2 的 8 张（会话/消息/方案/版本/特质/staging/用户/变更审批）。
**Service 唯一写库**是防数据腐蚀的架构约束：ID 生成、状态机校验、留痕逻辑只写一处；
工具函数、API、脚本都只能调 Service。审计时能一眼断定「数据是谁在什么规则下写的」。

### Q7：审批流怎么设计的？为什么不让 Agent 直接改？

商单预算/负责人是**资产数据**，LLM 直接 UPDATE 不可接受（幻觉/误操作无兜底）。
设计：Agent 只能 `request_deal_change` 建**申请**（捕获旧值快照）→ 审批中心人工批准 →
Service 原子写回 deal + 跟进流水留痕（谁批的、旧→新值）。一商单可挂多审批互不阻塞。
这是 Human-in-the-loop 从「方案确认」扩展到「数据变更」的自然延伸。

### Q8：数据重建踩了什么坑？

真实 Excel 比仿真数据脏得多，三个代表性问题：

1. **多子表纵向拼接**：一个 sheet 里 5 段不同列结构的子表，固定列映射必错——
   写了位置感知解析器，按单元格特征逐行重定位（粉丝/价格/类目白名单判断），错位行 6789 → 0
2. **str(None) 陷阱**：空单元格经 `str()` 变 `"None"` 字符串入库 9338 条脏流水——
   统一 `clean_str()` 防线
3. **psycopg `%` 格式符**：SQL 内联 `CURRENT_DATE-%s+%s` 被当格式符，占位符反复错位——
   一律纯 `%s` 参数 + Python date 对象

### Q9：Reranker 和向量检索什么区别？候选数为什么这么定？

| | 向量召回（Bi-Encoder） | Rerank（Cross-Encoder） |
|---|---|---|
| 结构 | query/doc 分别编码算余弦 | 拼接后整体过模型，token 级交互 |
| 速度 | 快（可预计算索引） | 慢（每候选前向一次） |
| 角色 | 粗排取 Top-N | 精排对 N 个细排 |

v2 语料 2063 块下 rerank 增益 **MRR +0.044**（0.744→0.788）是单组件最大贡献。
实测过候选裁剪（rerank_cand_k=10 vs 30）：v1 语料上耗时 -16.6% 精度不降，v2 一轮语料下有损弃用，
类目归一化后的终版语料下**持平略优（MRR 0.790 vs 0.788）且省 15% 耗时**——
同一参数在三轮语料上结论各不相同，**优化结论是数据相关的，每次换语料必须重测**，最终采用 cand_k=10。

### Q10：数据是怎么构造的？为什么不用公开数据集？

MCN 商单数据涉商业机密，公开渠道没有。分三层：

- **平台规则/方法论**：星图公开规则 + 行业报告改写为内部 SOP（12 条评测题的出处）
- **结构化台账**：正式 Excel 14289 达人重灌（脱敏）+ 400 商单（按「单价上限 + CPM 目标 + 平台差异」真实甲方逻辑生成）+ 100 甲方（30 品类）
- **非结构化语料**：结案商单**由库内 result_metrics 渲染**成案例文档——文档与台账天然一致，引用可验证

### Q11：你是如何定位「同构文档淹没」问题的？

现象：刊例类问题 Hit@5 异常低。排查：打印向量路与 BM25 路的**各路排名**，
发现美妆刊例表向量路第 1、RRF 后第 15——45 份同构跟踪单在两路都大量上榜，
`1/(k+rank)` 累加后数量优势盖过单篇高相关。修复：按 doc_id 限流（每文档最多 2 块）。
v2 语料上该问题更严重（1134 块在途单），去重组件保留，但**修过一次真 bug**：
限流最初作用在 RRF 融合前的两路列表（丢弃超限块），会污染融合分让正确文档沉底
（消融③组 Hit@1 崩至 0.316）；py-spy 抓栈+单例块级追踪定位后，移到融合后的候选池做
（保序+溢出移队尾不丢弃）→ ③ 恢复 0.740。**教训：组件在管线中的位置比组件参数影响大得多。**

## 四、数据与口径的诚实边界（面试被追问时的准确说法）

**数据构成（三层，各层可信度不同，主动讲清反而是加分项）：**

- **达人库 14289**：真实 Excel（双 sheet 21000+ 行）清洗重灌，含脱敏（手机号前3后4、微信号 sha1 不可逆）、位置感知解析、分成编码——**真实数据底座**
- **商单 400 / 甲方 100**：按**真实业务规则构造**（预算=达人单价上限、CPM 锚定星图行业区间、平台间差异、需求卡字段齐备）——不是随机造数，是业务经验的数据化；涉密真实商单本就不可外流，用真实规则仿真是该场景下的标准做法
- **案例语料 70**：由库内 result_metrics **确定性渲染**（非 LLM 生成），文档与台账天然一致、引用可验证

**评测口径（引用任何数字必须带的上下文）：**

- 消融指标口径：Hit@1 0.694 / MRR 0.788 ＠ 语料 2063 块、评测集 98 条（与语料同源反查生成）
- RAGAS 为 20 条抽样结论；faithfulness 部分样本因拒答/极短回答计 NaN，非幻觉
- context_recall 0.559 仅统计有 ground_truth 的 14 条

**已知待改进（被动问到再讲，主动讲要配方案）：**

- LLM 工具选择非 100% 服从：已用 docstring 强化 + 确认卡关口缓解，彻底方案是 LangGraph state 确定性分发（有明确改进路径，不是悬而未决）
- 评测集与语料同源生成存在偏乐观风险：缓解方式是评测集**动态反查当前库**（语料一变评测集跟着重建，不做一次性手工题库）
