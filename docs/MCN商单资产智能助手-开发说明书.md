## 一、项目背景

### 1.1 业务痛点

MCN / 星图服务商（广告代理商）的核心资产不是达人资源本身，而是**历史商单的沉淀**：
每个商单的报价谈判过程、达人组合效果、执行节奏、踩过的坑。但现实中这些资产以
**散落的文档形式**存在，导致三个高频问题：

| 痛点 | 具体表现 | 代价 |
|---|---|---|
| **资产不可复用** | 新商单来时，策划只能凭记忆找「以前类似的单子怎么做的」 | 重复造轮子，方案质量取决于个人经验 |
| **刊例与规则查不准** | 达人报价、平台规则、类目方法论散在 100+ 份文档里 | 商务反复问同事，报价口径不一致 |
| **在途风险看不见** | 45 个在途商单谁卡住了、卡了几天，靠人肉翻台账 | 商单超期才发现，客户关系受损 |

### 1.2 立项思路

**不做通用聊天机器人，做「私域资产 + 可溯源」的业务助手。** 三条设计原则：

1. **私域优先**：全部知识来自公司内部资产库（刊例表 / 历史商单 / 平台规则 / 方法论），
   不用公网知识 —— 因为商单报价和客户信息是敏感的，且通用模型不知道这家公司谈过什么价。
2. **可溯源到底**：每条结论必须带引用编号，`reports/e2e_proposal.md` 可核对。
   （原文直链的取值函数 `storage.presigned_url` 已实现，但**前端尚未接入**，属已知缺口）
   这是 B 端助手能否被信任的分水岭：商务敢不敢把方案直接发给广告主，取决于它敢不敢标注来源。
3. **人在环中**：方案生成必须经过运营确认/修改才定稿。
   业务上，商单方案涉及报价与客户承诺，不可能让 AI 直接对外输出。

### 1.3 目标岗位与能力映射

面向 **AI 大模型应用开发工程师（RAG / Agent 方向）**：

| 招聘要求关键词 | 本项目对应实现 |
|---|---|
| RAG 检索增强 | 混合检索链路（检索层 7 步 + 编排层意图路由）+ 自建 54 条评测集 + 8 组消融实验 |
| 多路召回与融合 | Milvus 向量 ∥ BM25 → 元数据预过滤 → 文档级去重 → RRF 融合 |
| Rerank 精排 | DashScope `gte-rerank-v2`，含候选池裁剪优化 |
| LangGraph / Agent 编排 | 10 节点 StateGraph + `interrupt()` 真人工介入 + 断点续跑 |
| Prompt 工程 | 5 个场景化系统提示词 + JSON 结构化输出 + 防幻觉约束 |
| 评测体系 | 54 条带 ground-truth 评测集，Hit@k / MRR / Recall@k |
| 工程化 | 三存储协同（向量+关系+对象）、依赖裁剪、端到端验收 |

### 2.2 技术选型与理由

| 层 | 选型 | 为什么选它 |
|---|---|---|
| LLM | DeepSeek（火山方舟 ARK `/api/plan/v3`） | 中文业务理解强，JSON 输出稳定，成本低 |
| Embedding | 本地 Ollama `bge-m3`（1024 维） | **离线零成本**；批量离线调用、延迟不敏感；换本地前已做对照验证 |
| Rerank | 阿里云 DashScope `gte-rerank-v2` | **查询链路上、延迟敏感**，实测 35ms/条（30 条候选单次调用中位 1051ms）；本地 CPU 1126ms/条 |
| 向量库 | Milvus（HNSW + COSINE + 5 倒排索引） | 原生混合检索、元数据过滤、标量索引 |
| 关系库 | PostgreSQL 18.6 | 台账类数据要事务与聚合；BM25 语料也从这里取 |
| 对象存储 | MinIO | 存放文档原件，预签名直链供前端「查看原文」 |
| 编排 | LangGraph | 需要**状态机 + 中断 + 断点续跑**，不是线性链 |
| 前端 | Streamlit | 内部工具，快速交付；三 tab 够用 |

### 2.3 Rerank 选型过程（本项目最有价值的工程决策）

分三阶段，**用数据否掉了看似更专业的方案**：

| 阶段 | 方案 | 实测结果 | 结论 |
|---|---|---|---|
| ① | 本地 `sentence-transformers` + `bge-reranker-v2-m3` | CPU **1126 ms/条**，一次消融 60+ 分钟 | 太慢，不可接受 |
| ② | 同上，GPU 加速（GTX 1650 Ti 4GB） | fp32 **OOM**；fp16 **3225 ms/条（比 CPU 还慢 3×）** | 显存耗尽导致权重反复搬运，硬件限制 |
| ③ | 云端 DashScope `gte-rerank-v2` | **35 ms/条（32.1×）**，且 Hit@1 0.741→0.778 | **采用** |

② 的根因：实测启动前可用显存仅 **free 1.16G / 4.00G**（`reports/gpu_rerank_bench.log`），
即桌面与系统组件已占用约 2.84G，不足以承载 fp32 权重（未跑通）；
换 fp16 后加载阶段被吃满（`free 2.35G → free 0.00G`，`reports/gpu_fp16_bench.log`）。
这是**客观硬件限制**，不是配置错误。

③ 的额外收益：移除 `torch` / `transformers` / `sentence-transformers` 共 3.9GB 依赖，
venv 从 **1.3G 降到 660M**。

### 2.4 Embedding 为什么保留本地（先验证再切换）

对比本地 `bge-m3` 与原云端方案的向量统计量后确认无损，才重建全部 457 条索引：

| 检查项 | 结果 | 判读 |
|---|---|---|
| 向量标准差 | 两者均 0.03124 | 分布尺度一致 |
| 跨模型余弦相似度 | 0.9205 | 高度同源 |
| 语义区分度（同类 vs 异类） | 本地 0.2838 / 云端 0.2753 | 本地略优 |

分工逻辑：**Embedding 批量离线、延迟不敏感 → 本地零成本；Rerank 在线链路、延迟敏感 → 云端。**

## 三、核心功能

### 3.1 功能一：商单构思生成（proposal）

**业务价值**：把「策划凭经验想方案」变成「检索同类历史商单 → 数据支撑方案」。

**流程**：

```
自然语言需求
  → parse_requirement   抽取结构化字段（类目/预算/达人量级/平台/目标）
  → retrieve_cases      检索相似历史商单（含效果数据）
  → match_kol           按类目+粉丝量级匹配候选达人（SQL 查询，非向量）
  → generate_proposal   生成 7 段式方案（含引用）
  → human_review        【人工介入】运营确认或提修改意见 ⟲ ≤3 轮
  → finalize            定稿
```

**需求解析字段**（`parse_requirement` 输出）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `brand` | str\|null | 广告主名称 |
| `category` | str | 类目（美妆/母婴/3C数码/食品饮料/服饰/家居/汽车/游戏） |
| `sub_category` | str\|null | 二级类目 |
| `budget` | int\|null | 统一换算为人民币元（"15万" → 150000） |
| `kol_count` | int\|null | 达人数量 |
| `kol_tier` | str | 头部/腰部/尾部/不限 |
| `platform` | str | 抖音/小红书/快手/不限 |
| `target_audience` | str\|null | 目标人群 |
| `campaign_goal` | str | 带货/种草/曝光/新品发布 |
| `hard_constraints` | list[str] | 硬性约束 |

**输出方案结构**（7 段式）：
需求理解 → 达人组合建议（表格）→ 执行节奏 → 预算分配表 → 效果预估与依据 → 风险提示 → 参考来源

**实测**：方案 3557 字，引用 `[1..5]` 无越界，8 位候选达人。

### 3.2 功能二：刊例 / 案例速查（query）

**业务价值**：替代「翻 100 份文档」和「问同事」，且带引用可核查。

**两类典型问题**：
- 规则/方法论类：「商单立项的预算怎么分配？」
- 数值/条件过滤类：「美妆类目 10 到 50 万粉的达人报价？」

**防幻觉三道闸**：

1. **Prompt 铁律**：只依据 `<context>` 作答，禁止外部知识；数值必须原样引用，不得四舍五入。
2. **代码级引用校验**（`validate_citations`）：检查引用编号是否越界，`[6]` 在只有 5 条上下文时判为无效。
3. **无依据强制拒答**（`enforce_unknown_on_empty`）：上下文为空时，代码层强制替换为明确拒答语，不交给模型自由发挥。

**引用重试机制**：首次生成若引用校验不通过，携带校验反馈重试一次（`_answer_with_citation_retry`）。

**实测**：两问均命中 5 片段并带引用；无依据时明确声明「知识库中未找到相关依据」+ 零引用。

### 3.3 功能三：在途商单跟进与风险预警（followup）

**业务价值**：从「人肉翻台账」变成「主动扫描 + 可发送话术」。

**风险规则**（由代码计算停滞天数，LLM 只负责解释与措辞 —— 关键设计）：

| 条件 | 风险等级 |
|---|---|
| 停滞 ≥ 7 天，或计划结案日已过仍未结案 | 高风险 |
| 停滞 ≥ 3 天 | 中风险 |
| 其他 | 正常 |

> **为什么规则用代码不用模型**：数值判定必须确定性可复现。让 LLM 算天数会引入不可控误差，
> 且无法向客户解释。模型只做它擅长的：归因（为什么卡住）与措辞（怎么跟同事说）。

**输出结构**：`summary` + `at_risk[]`（每条含 `deal_id` / `brand` / `stage` / `stagnant_days` /
`risk_level` / `reason` / `suggested_action` / `message_draft`）

**实测**：在途 45 单（高 18 / 中 16 / 正常 11），输出 15 条建议，全部含可发送话术。

### 3.4 人工介入（Human-in-the-Loop）

**实现**：LangGraph `interrupt()` + `MemorySaver` Checkpointer。

- 图在 `human_review` 节点真正挂起（`next=('human_review',)`），进程可退出后再恢复
- 运营可「确认定稿」或「提修改意见」，后者走 `revise` 节点重生成并再次中断（≤3 轮）
- **实测**：修改按钮生效（`revision_count=1`）；确认后图正常结束（`next=()`）

> **中断机制是真的**：`interrupt()` 使图真正挂起（`next=('human_review',)`），不是模拟。
> **但持久化取决于注入的 Checkpointer**：默认兜底 `MemorySaver`（内存态，进程退出即丢），
> 设置 `LANGGRAPH_CHECKPOINT_SQLITE=<path>` 即切到 `SqliteSaver`，此时可真正跨进程恢复。
> 跨进程续跑已由 `scripts/demo_cross_process_resume.py` 用三个独立进程演示验证。

### 4.4 分块策略（父子双层）

```
文档 → 按 ## 小节切分 → 每个小节生成 1 个父块（完整小节内容）
                      → 小节内按段落切子块（MAX_CHARS=560, OVERLAP=80）
                      → 子块入 Milvus（检索粒度）+ PG chunk_meta（元数据）
                      → 父块入 PG parent_chunk（生成粒度）
```

**为什么父子双层**：小块检索准（语义聚焦），大块生成全（上下文完整）。
命中子块后 `expand_to_parent` 回溯父块，既保证召回精度又给足生成上下文。

## 五、Prompt 设计

全部提示词位于 `src/starmoyu/assistant.py`（4 个）与 `graph.py`（1 个），共 **5 个**。
设计原则：**约束写在铁律里，格式写在 Schema 里，判定交给代码。**

### 5.1 设计原则

| 原则 | 做法 | 为什么 |
|---|---|---|
| 防幻觉前置 | 「只依据 `<context>`，禁止外部知识」写进铁律第 1 条 | 提示词是防线第一层，代码校验是第二层 |
| 数值不可变 | 「必须原样引用，不得四舍五入改写或估算」 | 报价/粉丝量失真会直接导致商务事故 |
| 拒答有出口 | 「无依据必须明确说『未找到』，并说明缺什么」 | 不给模型编造的空间，也避免它硬答 |
| 结构化输出 | 明确 JSON Schema，含字段类型与枚举 | 下游要解析，自由文本无法程序处理 |
| 判定归代码 | 停滞天数由脚本算，模型只解释与措辞 | 数值判定必须确定性可复现 |
| 可迁移不硬套 | 「类目不同需指出差异，不要硬套」 | 跨类目经验迁移是真实业务难点 |

### 5.2 `SYS_QA` —— 速查问答（防幻觉最强约束）

```
你是 MCN 商单资产的资深运营助理，服务对象是商单运营与商务同事。

## 铁律
1. 只依据 <context> 中的信息作答，不得使用任何外部知识或常识推断。
2. 每条事实性结论后必须紧跟引用编号，格式 [1]、[2] 或 [1][3]。
3. 若 <context> 中没有足够信息，必须明确回答「知识库中未找到相关依据」，
   并说明缺什么，禁止编造。
4. 涉及金额、比例、天数、粉丝量等数值时，必须原样引用，不得四舍五入改写或估算。
5. 不得引用 <context> 中不存在的编号。

## 输出格式
先给出结论，再给依据。结尾固定输出：
### 参考来源
[1] {文档标题} · {小节} · {来源文件}
```

**设计要点**：铁律 5 是「引用不得越界」，与代码层 `validate_citations` 形成双保险 ——
提示词防君子，代码防小人。

### 5.3 `SYS_PROPOSAL` —— 方案生成（业务约束最重）

```
你是资深 MCN 商单策划，负责基于公司私有历史商单资产，
产出可直接给广告主看的商单构思方案。

## 铁律
1. 所有结论必须能追溯到 <context>，用 [1][2] 标注来源。
2. 报价只能来自 <context> 中的刊例或历史商单，禁止自行估算；
   若无依据，写「暂无刊例依据，需商务确认」。
3. 达人数据（粉丝量、互动率、报价）必须来自 <candidate_kols> 或 <context>，不得编造。
4. 效果预估必须写明依据（引用历史同类商单数据），不得凭感觉给数字。
5. 若检索到的历史商单与当前需求类目不同，需指出差异并说明可迁移的经验，不要硬套。

## 输出格式（Markdown）
## 一、需求理解
## 二、达人组合建议
| 达人ID | 昵称 | 量级/粉丝 | 匹配理由 | 刊例价 | 预估曝光 |
## 三、执行节奏
## 四、预算分配表
## 五、效果预估与依据
## 六、风险提示
## 七、参考来源
```

**设计要点**：铁律 5 针对真实业务痛点 —— 当用户问「汽车类目」（库里只有美妆案例）时，
模型必须**承认差异**而非硬套美妆数据。这是 B 端助手可信度的关键。

### 5.4 `SYS_ROUTER` —— 意图路由

```
你是意图分类器。判断用户问题属于哪一类，只输出 JSON。

类别定义：
- proposal：需要生成/设计商单构思方案（如"帮我做个方案""怎么策划这次投放"）
- query：查询类，问规则/报价/案例/数据（如"报价多少""有什么规则""做过哪些案例"）
- followup：查询在途商单状态与跟进建议（如"哪些商单卡住了""跟进情况"）
- chat：寒暄或与业务无关

输出：{"intent": "上述四类之一", "reason": "一句话理由"}
```

**设计要点**：给了**反例**（"帮我做个方案"）而不只是类名 —— 分类任务里样例比定义有效。
四分类决定后续走完全不同的子图，路由错误代价高。

### 5.5 `SYS_PARSE` —— 需求结构化抽取

```
你是 MCN 商单需求解析专家。将自然语言需求抽取为结构化字段。

严格要求：
1. 只输出 JSON，不要任何解释文字
2. 无法确定的字段填 null，禁止编造
3. budget 统一换算为人民币数字（元），"15万" → 150000
4. category 必须从以下选取：美妆/母婴/3C数码/食品饮料/服饰/家居/汽车/游戏

输出 Schema：
{"brand": "广告主名称或 null", "category": "类目", "sub_category": "二级类目或 null",
 "budget": 数字或 null, "kol_count": 整数或 null, "kol_tier": "头部/腰部/尾部/不限",
 "platform": "抖音/小红书/快手/不限", "target_audience": "目标人群或 null",
 "campaign_goal": "带货/种草/曝光/新品发布", "hard_constraints": ["硬性约束"]}
```

**设计要点**：规则 3 处理中文数字口语（"15万"），规则 4 用**枚举锁定**类目
—— 防止模型输出「美妆个护」这类不在库里的类目名，导致后续元数据过滤全部失效。
规则 2 用 `null` 而非编造，配合下游 SQL 的「字段为空则不加该过滤条件」逻辑。

### 5.6 `SYS_FOLLOWUP` —— 跟进分析与话术

```
你是商单跟进助理。基于在途商单数据识别风险并生成跟进建议。

## 判断规则（停滞天数已由脚本计算，你负责解释与措辞）
- 停滞 ≥ 7 天，或计划结案日期已过仍未结案 → 高风险
- 停滞 ≥ 3 天 → 中风险
- 其他 → 正常

## 要求
1. 建议话术要专业、简洁，可直接复制发送给同事。
2. 只基于输入数据，不得编造商单信息。
3. 只输出 JSON。

## 输出结构
{"summary": "整体情况一句话", "at_risk": [{"deal_id": "...", "brand": "...", "stage": "...",
 "stagnant_days": 数字, "risk_level": "高/中/正常", "reason": "...", "suggested_action": "...",
 "message_draft": "可直接发送的话术"}]}
```

**设计要点**：括号里那句「停滞天数已由脚本计算，你负责解释与措辞」是**职责边界声明**
—— 明确告诉模型不要重算，避免它在数值上发挥。`message_draft` 要求「可直接复制发送」
是把 AI 输出落到可用交付物上，而非停留在分析。

### 5.7 提示词与代码的配合关系

| 提示词约束 | 代码层配套 | 文件位置 |
|---|---|---|
| 「不得引用不存在的编号」 | `validate_citations()` 校验越界 | `assistant.py:104` |
| 「无依据必须拒答」 | `enforce_unknown_on_empty()` 强制替换 | `assistant.py:119` |
| 「必须带引用」 | `attach_sources()` 由代码确定性渲染来源区块 | `assistant.py:93` |
| 「只输出 JSON」 | `_repair_truncated()` 修复被 max_tokens 截断的 JSON | `assistant.py` |
| 「模型只解释不判定」 | 停滞天数由 `followup()` 脚本计算后传入 | `assistant.py:268` |

> **核心思路**：提示词负责「引导」，代码负责「保证」。
> 凡是能确定性验证的（引用越界、JSON 合法性、数值边界），一律不依赖模型自觉。

## 六、检索链路与实测效果

### 6.1 八步链路

```
Query → 意图路由 → 多路召回（Milvus 向量 ∥ BM25）→ 元数据预过滤
      → 文档级去重 → RRF 融合 → 文档类型先验 → 类型配额保底
      → Rerank（gte-rerank-v2）→ 引用组装
```

| 步骤 | 关键参数 | 作用 |
|---|---|---|
| 多路召回 | `cand_k=30` | 向量与 BM25 各取 30 条 |
| 文档级去重 | `max_per_doc=2` | 每文档最多 2 块，防同构文档淹没 |
| RRF 融合 | `k=60` | 排名融合，免调权重 |
| 类型配额保底 | `quota_per_type=3` | 高先验文档类型保障名额 |
| Rerank | `rerank_cand_k=10` | 送入 reranker 的候选数（可裁剪） |

### 6.2 八组消融实验结果

评测集 54 条，逐组件叠加（数字来自 `reports/ablation_dashscope.log`）：

| 实验组 | Hit@1 | Hit@3 | Hit@5 | Hit@10 | Recall@5 | MRR | 耗时 |
|---|---|---|---|---|---|---|---|
| ① 纯向量召回 (Baseline) | 0.667 | 0.889 | 0.907 | 1.000 | 0.880 | 0.784 | 139.3s |
| ② + BM25 多路召回 (RRF) | 0.667 | 0.907 | 0.926 | 0.944 | 0.883 | 0.781 | 137.3s |
| ③ + 文档级去重 | 0.667 | 0.907 | 0.907 | 0.944 | 0.894 | 0.780 | 137.8s |
| ④ + 元数据预过滤 | 0.667 | 0.889 | 0.907 | 0.926 | 0.884 | 0.773 | 138.6s |
| ⑤ + 文档类型先验 | 0.685 | 0.889 | **1.000** | 1.000 | 0.963 | 0.802 | 149.9s |
| ⑥ + 类型配额保底 | 0.741 | 0.963 | **1.000** | 1.000 | 0.963 | 0.849 | 152.1s |
| ⑦ + Rerank (cand_k=30) | **0.778** | 1.000 | 1.000 | 1.000 | 0.981 | 0.880 | 212.4s |
| ⑧ **+ 收窄重排候选 (=10)** | **0.778** | 1.000 | 1.000 | 1.000 | **0.986** | **0.883** | **177.2s** |

**完整链路（⑧）相对基线（①）**：MRR **+0.099**、Hit@1 **+0.111**、Recall@5 **+0.106**

### 6.3 两个关键结论（面试可讲）

**结论 1：组件增益非单调。** ②③④ 相对基线在 Hit@5/MRR 上**略有回落**。
根因：BM25 单路融合会引入同构文档干扰 —— 45 份结构相似的跟踪单以数量优势主导融合分数。
必须配合文档级去重（③）与文档类型先验/配额（⑤⑥）才转正。
**这说明「多路召回 + RRF」不是无脑加分的银弹，需要配套治理。**

**结论 2：先量测再优化。** 实测 GT 文档在**重排前**候选池 top-5 内命中率已达
**54/54 = 100%**，说明候选池大部分条目对最终 Top-K 无贡献却要付等量重排开销。
新增 `rerank_cand_k` 只收窄送入 reranker 的候选数（不动召回池），
结果**耗时 -16.6% 且 MRR/Recall@5 反而微升**。
