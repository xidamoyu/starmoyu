## 四、检索管线七阶段（源码实测）

`src/starmoyu/retriever.py::Retriever.search()`：

```
query
 ├─1 双路召回   retrieve_vector(cand_k)  ← Milvus HNSW/COSINE + 标量预过滤
 │              retrieve_bm25(cand_k)    ← jieba 分词 + BM25Okapi
 ├─2 元数据过滤 meta_filter()             ← 从 query 解析类目/粉丝区间/年份，命中不足 3 条则放行
 ├─3 RRF 融合   rrf(k=60)                ← 1/(60+rank+1) 累加两路
 ├─4 类型先验   doc_type_prior()          ← 查询关键词→doc_type 权重（报价→rate_card 2.0 等）
 ├─5 文档去重   dedupe_by_doc(max_per_doc=2) ← 保序+溢出移队尾（不丢弃）
 ├─6 类型配额   strong prior(≥1.5) 保留 3 个候选名额
 ├─7 截断+重排  cands[:rerank_cand_k] → gte-rerank-v2 → 完整结果上再做一次类型提升 → top_k
 └─ build_context(max_chars=4000) → 带编号的上下文 + 引用元数据
```

关键设计点（都写在源码注释里，可对照）：
- **去重位置**：必须在 RRF 融合**之后**。融合前做会改变各路原始排名、污染 RRF 分数（曾致消融③组 Hit@1 崩到 0.316）。
- **配额与提升**：重排模型会被同构文档的字面相似片段误导（跟踪单里也写着"报价 ¥58,300"），
  所以既要在候选阶段保留名额，也要在重排完整结果上做一次类型提升，再截断 top_k。
- **父块扩展**：检索命中子块后，`expand_to_parent()` 取父块拼上下文，子块用于匹配、父块用于生成。

## 六、数据流动全图

### A. 对话主链（最核心）
```
浏览器 ChatView
  │ 1. POST /api/chat/{conv_id}  body: {text, deal_id?, attachments[]}
  ▼
api.py::chat
  ├─ 附件处理：base64 解码 → MinIO 留档 → chat_vision(qwen-vl) 转写 → 拼进 user_text
  ├─ cs.add_message(conv_id,"user",user_text)        → messages 表
  ├─ cs.maybe_autotitle(conv_id)                     → 首问提炼会话标题
  ├─ body.deal_id → m6.pin_deal()                    → conversations.pinned_deal_id
  └─ SSE 生成器 gen()
       ├─ 先推 event: deal_context（钉住状态 / 正则检测到的商单号）
       ├─ 再推 event: attachments（附件元数据）
       └─ for ev in agent.chat_stream(conv_id, user_text, pinned_deal_id):
            token      → 前端逐字累加
            tool_call  → 前端渲染工具卡片
            tool_result→ 前端显示结果预览 + 正则提取商单号推关联提示
            写回：cs.add_message(conv_id,"assistant",全文)
```
前端 SSE 事件类型共五种：`deal_context` / `attachments` / `token` / `tool_call` / `tool_result` / `done` / `error`。

### B. Agent 循环内部
```
agent_node(state)
  ├─ 若无 SystemMessage → 注入 SYSTEM_PROMPT（2851 字符）
  ├─ 选路：首轮 + 无工具历史 + 无钉单 + _is_chitchat(≤14字且不含业务词白名单)
  │     ├─ 是 → model_light.invoke()（关思考链、不挂 24KB 工具 schema）
  │     └─ 否 → model.invoke()（19 工具全绑 + 思考链）
  └─ 返回 {"messages":[AIMessage]}
        │
        ├─ _should_continue: AIMessage.tool_calls 非空 → "tools"
        │                                       否则 → END
        ▼
tools_node = ToolNode(19 工具, handle_tool_errors=可读文本)
        │
        └─ add_edge("tools","agent") → 结果回喂 → 循环（recursion_limit=25）
```

### C. 一次业务写操作的全链（以「沉淀达人经验」为例）
```
用户粘贴聊天记录
  → Agent 抽取特质清单展示（不写库）
  → 用户回"确认"
  → Agent 调 save_interaction(kol_name, raw_text, traits)
      → m4_service（deals 三处原子写）
           ├─ ingest_staging.raw_content         原始留档
           ├─ party_traits (verified=TRUE)       结构化特质
           └─ deal_followup (action_type=note)   跟进记录
  → 下次问"这个达人靠谱吗" → list_kol_traits → 只列原文条目（零生成）
```

### D. 结案回流飞轮（写→读闭环）
```
结案确认卡/表单
  → save_deal_result → deal.result_metrics 回填 + stage='结案' + deal_followup 留痕
  → 返回 hint「建议沉淀」
  → Agent 主动提议 → sediment_case(confirm=false) 出预览
       ├─ 读 deal + deal_followup → 渲染案例 Markdown（含流水提炼的复盘经验）
       └─ 返回草稿标题 + 要点
  → 用户确认（可补 extra_lessons）
  → sediment_case(confirm=true)
       ├─ 幂等检查（同 deal_id 旧块先删）
       ├─ 切块（父子双层）→ embed(bge-m3) → PG chunk_meta/parent_chunk + Milvus
       └─ MinIO 存原文
  → 下一次 search_knowledge 立即可召回（实测 DC20250005 沉淀后秒级召回 top1）
```

### E. 商单变更审批流
```
用户在对话里说"把预算改成 15 万"
  → Agent 无权限直改 → request_deal_change(field_name='budget', new_value=150000)
      → deal_change_requests (status=pending, old_value 快照, created_by)
  → 审批中心「商单变更」标签页展示
  → 管理员批准 → POST /api/deal-changes/{id}/approve
      → 写回 deal.budget + deal_followup(action_type='字段变更审批', 含旧→新)
      → status=approved, reviewed_by/at
  → 驳回则 status=rejected，deal 不动
```

### F. 导入三通道 + 双审
```
上传文件
  ├─ kind=kols  → 直接 ON CONFLICT 入 kol_profile（低风险结构化）
  ├─ kind=deals → ingest_staging(suggested_kind=import_deal) → 双审 → deal 表
  └─ kind=docs  → ingest_staging(suggested_kind=import_doc)  → 双审 → 切块向量化入 RAG
双审：POST agent-review（LLM 质检 → pass/warn/reject + issues 清单）
      → POST confirm（管理员确认，reject 单需二次确认）或 reject（驳回）
```

## 六之二、关键事件 → 图节点 → 工具 → 落库表（全映射）

### 先明确图里只有两个节点，所有事件都走同一条路

```
START → agent ─┬─(有 tool_calls)→ tools ─┐
               └─(无 tool_calls)→ END    │
                     ▲                    │
                     └────────────────────┘
```

**没有任何事件有专属节点**。事件之间的差别全部在 `agent_node` 内部的三件事上：
① 走重模型还是轻模型；② 模型选哪个/哪几个工具；③ 工具内部写哪张表。
所以下面这张表可以逐行对着代码验证——`节点` 列只有 `agent` / `tools` 两个值。

### 事件全映射表

| 用户事件（自然语言） | 节点序列 | 调用的工具 | 写入的表 | SSE 事件 |
|---|---|---|---|---|

| 问报价/规则/流程/案例 | agent → tools → agent | search_knowledge | 无（只读） | tool_call / tool_result / token |

**这张表的三个结论**：
1. **对话内的一切都走 `agent → tools` 同一循环**，没有分支节点、没有 router。
2. **凡是有表单 UI 的动作，都不经 LLM**（改阶段/结案/加跟进/审批/导入）——这是刻意的：
   表单是确定性路径，零幻觉风险；对话是自然语言路径，靠确认卡把关。
3. **写操作的落库全在工具内部**（调 service 层），节点本身不写库。

### 单轮对话的节点级时序（以「3C 数码 10 万预算 3 个达人出方案」为例）

```
POST /api/chat/{conv_id}                     [api.py]
 ├ messages += user_msg                      [PG]

    ├─ 构造 HumanMessage(pinned_deal_id 注入 cfg)
    ├─ node: agent        第 1 次进入  ← 注入 SYSTEM_PROMPT，绑 19 工具
    │   └ AIMessage.tool_calls = [match_kols_for_requirement]
    ├─ node: tools        执行 1       ← match_kols_for_requirement 直查 PG kol_profile
    │                                     （按 类目 + 均摊单价 0.85 过滤，带历史 ROI 子查询）
    │   └ ToolMessage(候选达人 JSON)
    ├─ node: agent        第 2 次进入  ← 带着达人结果再决策
    │   └ AIMessage.tool_calls = [create_proposal]
    ├─ node: tools        执行 2       ← 写 proposals + proposal_versions
    │   └ ToolMessage(proposal_id)
    ├─ node: agent        第 3 次进入
    │   └ AIMessage(无 tool_calls) = 最终答复文本
    └─ END
共 5 个节点执行（agent 3 次 + tools 2 次），recursion 上限 25
```

## 七、工具绑定与匹配机制（回答「绑这么多工具怎么准确匹配」）

### 1. 匹配靠什么——四层信号，按权重递减

**第一层：工具描述里的「何时使用」段落（最强）**。19 个工具的 docstring 全部按统一结构写：
```
<一句话功能>
何时使用：<用户会说的自然语言场景，含具体说法>
Args: <每个参数的含义与取值范围>
```
例如 `get_deal_result` 的「何時使用」直接写：「用户问某商单"效果怎么样/ROI多少/GMV多少/结案数据"时，
**必须调用本工具（而不是 get_deal_status）**」——把最容易混的两个工具做了显式区分。
`search_kols` 的 `name` 参数描述里写「用户点名找某人时用它，不要换类目反复试」——
这条是修 25 步递归爆顶时加的，实测把同类问题从失控收敛到 2 次调用。

**第二层：参数 schema 的类型与枚举**。`tier`（头部/腰部/尾部）、`action`（approve/reject/revise）、
`field_name`（budget/owner/stage/...）用字面量约束，模型不需要猜取值范围。

**第三层：系统提示词的流程约束（2851 字符）**。四个业务流单独成节（沉淀流/结案复盘流/
结案沉淀流/Brief 接单流），每节写死「第几步必须调哪个工具、禁止用什么替代」。
例：Brief 流明确写「用户确认后**必须立即调用 save_brief（而不是 create_proposal）**」——
因为两个工具语义相近，是实测中真实混淆过的点。

**第四层：确认卡关口的代码兜底**。模型服从性不可能 100%，所以关键动作有代码兜底：
- `save_interaction` 的 `deal_id` 由后端从会话钉住状态注入（模型忘传也挂得对）
- 参数类型宽容：`traits` 声明为 `Any`，模型传 list 或 JSON 字符串都能处理，中英文键名都认
- 写库前人工确认：所有写工具都要求先展示、后调用，确认卡是硬关口

### 2. 为什么是 19 个而不是拆成多个 Agent

- **拆分成本**：多 Agent 需要路由 + 状态传递 + 错误恢复，而当前业务流是**串联**的
  （查知识库→查达人→出方案），单 Agent 循环天然支持任意串联。
- **schema 体积**：19 个工具的描述合计约 24KB，在 qwen3.8-flash 的上下文里占比可接受；
  实测工具选择准确率足以跑通 36 断言的全量回归。
- **真实代价**：工具越多，模型越容易「该调 A 时调 B」。缓解手段不是减少工具，
  而是上面四层信号——尤其第一层的显式互斥描述（"必须用 A 而不是 B"）。

### 3. 已知的匹配失败模式与缓解

| 失败模式 | 实例 | 缓解 |
|---|---|---|
| 该调写库工具却只做口头总结 | 用户确认后不调 `save_interaction` | 提示词写「绝不允许」+ 验收断言 |
| 两个相近工具混用 | `create_proposal` vs `save_brief` | 互斥描述 + 提示词点名 |
| 参数缺席导致盲扫 | 点名找达人时反复换类目 | 加 `name` 参数 + 描述里禁止换类目 |
| 多轮工具链爆递归 | 复杂问题 25 步上限 | `recursion_limit=25` + 工具描述收敛路径 |
| 服从性波动 | 「确认」后偶尔不调工具 | 单工具原子化（合并两步为一步）+ 验收多轮跑 |

### 4. 可验证手段

`scripts/` 下的验收脚本对工具调用做**行为断言**（不是只看回复文本）：
```
F6: 断言本轮 party_traits 行数不变（确认卡前零写库）
F6b: 断言调用 save_interaction 且 party_traits +3
F2a: 断言 tool_call 事件里出现 search_kols
```
这类断言把「模型是否真的调了工具」变成可回归的指标，而不是靠人工看对话。

## 八、权限与安全边界

| 层 | 机制 | 实测 |
|---|---|---|
| 认证 | JWT（HS256），`_jwt_sub` 取 sub，`_require_admin` 校验 role | operator 访问 admin 端点 403 |
| 越权防护 | 不能删自己、不能降级自己的 admin 角色 | 422 拦截 |
| 写权限分层 | 对话内 Agent **无权限改 deal 主字段** → 只能发变更申请 | `request_deal_change` |
| 敏感数据 | 手机号 `187****6504`、微信号 `wx:sha1前8`；账号 ID 不落库 | 明文手机号实测 0 条 |
| 幻觉防护 | ① 事实性回答必须基于工具返回 ② 数字原样引用不四舍五入 ③ 无依据明说 ④ 特质只列原文 | 数值保真 100%（24/24） |
| 导入防脏 | Agent 预审 + 管理员确认双闸；reject 单强制入库需二次确认 | 预算 -5000 的脏行被 reject |
