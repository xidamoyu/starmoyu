# MCN 商单资产智能助手 —— 检索与生成评估体系设计方案

> 文档定位：为已完成的项目设计一套**独立、可持续运行**的评估体系，覆盖评测集构建、检索质量评估、生成质量评估、消融实验设计、真实用户实测、生产口径性能指标六个部分。
> 所有指标给出**目标值或合格线**（带依据），不是实测值；实测结果以评测运行当日的落盘报告为准。
> 术语约定：检索增强生成（Retrieval-Augmented Generation，RAG）指「先从知识库检索相关内容、再让大语言模型基于检索内容回答」的技术路线；后文指标名首次出现均附全称与中文解释。

---

## 〇、评估对象与口径总纲

| 评估对象 | 组成 | 评估方式 |
|---|---|---|
| 检索管线（非结构化路） | 向量召回（BGE 系列 Embedding 模型，Milvus HNSW 索引）+ BM25 关键词召回 → 倒数排名融合（Reciprocal Rank Fusion，RRF）→ 文档级去重（每篇文档最多保留 2 个文本块）→ CrossEncoder 交叉编码器重排序 | 离线评测集 + 分组消融 |
| 结构化查询路 | SQL 精确过滤（类目 / 粉丝量级 / 报价 / 排他期），由大语言模型决定何时走这一路 | 工具调用正确性评测 |
| 生成层 | 对话回答基于检索上下文，数值强制引用、检索不到明确拒答 | RAGAS 四指标 + 业务规则校验 |
| 端到端 Agent | 19 个工具的多轮调用循环 | 任务完成率 + 线上行为埋点 |
| 性能 | 首字延迟 / 完整回答延迟 / 检索延迟 | P50 / P95 / P99 分位数 |

**三条评估纪律（适用于全部章节）：**

1. **评测集与语料解耦**：评测题目不允许从当前语料的文本块里直接摘抄生成，必须由「业务问题 → 人工标注相关文档」的正向流程构建；语料变更后评测集不自动失效，只有相关文档增删时才修订对应题目。
2. **口径先行**：任何被引用的数字必须同时说明评测集版本号、语料版本号、运行日期。不同口径的数字不可直接比较。
3. **回归纪律**：语料任何变更（新增 / 删除 / 重新切片）、管线任何参数变更（融合权重、去重上限、重排序候选数），必须全量重跑评测集并在报告中并列变更前后数字。

## 一、评测集设计（检索与生成共用的地基）

### 1.1 构建流程

评测集由三层来源构成，杜绝「从语料里抄答案再问语料」的自证偏乐观：

| 来源 | 构建方式 | 占比建议 | 防偏乐观机制 |
|---|---|---|---|
| 业务真实问题 | 从客服记录、商单跟进备注、销售问答中提取用户真实提法，人工改写成规范问句 | 约 40% | 用户的真实措辞与语料书面语言天然存在词汇鸿沟，是对检索最严苛的考验 |
| 领域专家出题 | 由熟悉商单业务的人（或依据星图平台公开规则、行业方法论）出题，**先出题、后标注答案文档** | 约 35% | 出题时不看语料，标注时才确定相关文档，避免「照着语料措辞出题」 |
| 对抗性题目 | 专门构造的易混淆对：相似类目（美妆 vs 美妆工具）、相似量级（腰部 vs 准头部）、同品牌不同商单、价格相近的不同刊例 | 约 25% | 检验管线区分同构文档的能力，这是本语料最大的风险点（数百份结构相似的跟踪单） |

### 1.2 难度分层（每道题必打标签）

| 层级 | 定义 | 预期难度 |
|---|---|---|
| L1 精确查找 | 问题中的关键词与目标文档高度重合（如「美妆类目刊例价」） | 低，检索失败的信号意义最强 |
| L2 语义改写 | 用户口语与文档书面语用词不同（如「达人现在大概什么身价」→ 刊例报价文档） | 中 |
| L3 多约束聚合 | 需要综合多份文档或先过滤再统计（如「母婴类目里历史投资回报率超过 2 的案例有几个」） | 高 |
| L4 否定 / 边界 | 语料中不存在答案，正确行为是拒答或说明无依据 | 高，专门考拒答能力 |

### 1.3 规模与维护

- **总量**：150 条（L1 40 条 / L2 50 条 / L3 40 条 / L4 20 条）。依据：每层至少 20 条才能让分项指标的波动小于 0.05（95% 置信区间下），总量控制在人工标注成本可承受的范围。
- **标注质量**：每道题的相关文档标注由两人独立完成，不一致的题目进入仲裁；相关性分三档（直接回答 / 部分辅助 / 无关），计算指标时「直接回答」计满分、「部分辅助」计 0.5。
- **版本管理**：评测集以文件入库（题目 + 标签 + 相关文档编号 + 标注人），任何修订追加版本号，历史版本不覆盖。

## 二、检索评估

### 2.1 指标体系（定义与目标值）

| 指标 | 定义 | 为什么用它 | 目标值（合格线） |
|---|---|---|---|
| Hit@1（第 1 条命中率） | 排名第 1 的结果即为相关文档的题目占比 | 用户绝大多数情况只看第一条回答依据 | ≥ 0.65（业界中等规模混合检索在域内语料上的常见水平 0.60–0.75） |
| Hit@5（前 5 条命中率） | 前 5 条结果中包含相关文档的题目占比 | 对话场景展示前 5 条参考来源 | ≥ 0.90 |
| MRR（Mean Reciprocal Rank，平均倒数排名） | 相关文档排名的倒数的平均值（排名第 1 得 1 分、第 2 得 0.5 分……） | 综合反映「找没找到」和「排多前」 | ≥ 0.75 |
| Recall@10（前 10 条召回率） | 相关文档（可多标注）被前 10 条覆盖的比例 | 多标注场景下保证重排序有足够候选 | ≥ 0.85 |
| NDCG@10（Normalized Discounted Cumulative Gain，考虑位置衰减的排序增益） | 按相关性分档和排名位置加权计算的排序质量分，归一化到 0–1 | 利用三档相关性标注，比二值指标更细腻 | ≥ 0.80 |

**分母口径**：全部指标只统计「语料中确实存在答案」的题目（L4 拒答题单独评估，见生成评估）；多相关文档的题目 MRR 取第一个相关位的倒数。

### 2.2 分层报告（禁止只报总平均）

每次评测必须输出按 L1–L4 分层的指标矩阵。理由：总平均会掩盖弱项——例如 L3 聚合题普遍偏低而 L1 拉高总分，只看总数会误判管线健康。**分层报告同时是行动指南**：L2 低说明 Embedding 的语义匹配不足；L1 低说明管线存在结构性缺陷（正常情况下 L1 应最容易）；L3 低优先改进查询改写而非检索参数。

### 2.3 消融实验设计（8 组对照）

每组只开关一个组件，其余固定；回答「该组件贡献了什么」：

| 组号 | 配置 | 回答的问题 | 预期结论方向 |
|---|---|---|---|
| ① | 纯向量召回 | 基线水平 | 全部组中最弱，是对照起点 |
| ② | 纯 BM25 | 关键词路独立价值 | L1 强、L2 弱——与①互补 |
| ③ | 向量 + BM25 融合 | 融合是否优于单路 | 应同时高于①②，否则融合权重有问题 |
| ④ | ③ + 文档级去重 | 去重对同构文档淹没的抑制 | 在跟踪单类题目上增益明显 |
| ⑤ | ④ + 重排序 | 重排序的精排贡献 | Hit@1 显著提升，MRR 提升幅度最大 |
| ⑥ | ⑤ + 查询改写（口语→书面语归一） | L2 层的专项改进 | L2 分层指标提升，其他层持平 |
| ⑦ | ⑤ − 去重（验证去重位置敏感性） | 去重作用于融合前还是融合后 | 融合前去重应明显劣于融合后（保序移队尾不丢弃）——该组固定为回归哨兵 |
| ⑧ | 完整管线 + 重排序候选数裁剪（只重排融合后前 10 条 vs 前 30 条） | 成本与质量的平衡点 | 质量持平（差异 < 0.005）则取小值以降低延迟 |

**执行纪律**：消融只在评测集版本升级或语料大版本变更时全量重跑；平时增量回归只需跑 ①⑤⑦ 三组（基线 / 完整 / 哨兵），约 20 分钟。

## 三、生成评估

### 3.1 RAGAS 四指标（框架：RAG Assessment，检索增强生成评估框架）

| 指标 | 衡量什么 | 评估的是管线哪一段 | 目标值 |
|---|---|---|---|
| 忠实度（Faithfulness） | 回答中的每个论断能否从检索到的上下文推出 | 生成层是否编造 | ≥ 0.90（近零幻觉是业务硬要求） |
| 答案相关性（Answer Relevancy） | 回答与问题的匹配程度 | 生成层是否答非所问 | ≥ 0.75 |
| 上下文精确率（Context Precision） | 检索到的上下文里相关内容的占比（相关内容是否排在前面） | 检索层排序质量 | ≥ 0.75 |
| 上下文召回率（Context Recall） | 回答所需的信息被上下文覆盖的比例 | 检索层召回质量 | ≥ 0.70 |

**抽样方案**：从评测集分层抽取 30 条（L1–L3 各 10 条），另加 5 条 L4 拒答题单独统计。理由：RAGAS 每条需要多次大语言模型调用做分解与判分，30 条在成本与置信度之间平衡；分层抽样保证弱项层不被淹没。

**判分模型与偏差控制**：判分用与被评管线不同的模型家族（避免自我偏好）；每季度抽 10% 样本人工复核判分结论，人工与大模型判分不一致率超过 15% 时更换判分模型。

**指标解读纪律**：忠实度高不等于回答正确——它只保证「没编造」，不保证「检索到的就是对的」（后者靠上下文召回率和人工标注的检索评测兜底）；列表型回答（「列出符合条件的达人」）在基于相似度的指标上天然偏低，分析时须按答案形态分组，不把结构性偏差误判为质量缺陷。

### 3.2 业务规则校验（RAGAS 覆盖不到的部分，代码确定性执行）

| 检查项 | 规则 | 合格线 |
|---|---|---|
| 数值保真 | 回答中的报价、投资回报率、粉丝数必须与数据库原值一致（正则抽取后比对） | 100%，出现一个不一致即判不合格 |
| 引用可溯 | 回答附带的「参考来源」与实际检索命中的文档一致（代码渲染，不允许模型自由生成） | 100% |
| 拒答正确（L4 专项） | 语料中无答案的题目，回答必须明确说明无依据；编造答案计严重不合格 | ≥ 95%，且编造案例逐条复盘 |
| 拒答不过度（L1–L3 专项） | 有答案的题目不允许错误拒答 | ≤ 2% |

### 3.3 工具调用正确性（结构化查询路）

构造 50 条带标准答案工具序列的用例（如「找美妆腰部达人」→ `search_kols(category=美妆, tier=腰部)`）：

- **路由正确率**：该走 SQL 路时走了 SQL、该走向量路时走向量 ≥ 95%；
- **参数正确率**：工具参数（类目、量级、价格上限）与问题约束一致 ≥ 90%；
- **重点回归**：点名查某达人的用例必须使用名字参数（历史缺陷：模型曾改用类目反复扫描直到耗尽步数，已在工具说明中修正）。

### 3.4 大语言模型裁判评分卡（主观维度）

对「表达清晰度 / 结构适合阅读 / 语气专业度」三项由大语言模型按 1–5 分打分，附评分理由。一致性校验：同一批样本隔周重评，分数相关系数 ≥ 0.85 才采信；否则视为评分不稳定，只做人工评审。

## 四、用户实测评估

### 4.1 任务式实测（Small-Scale User Study）

**设计**：招募 5–8 名目标用户（商单运营 / 商务同事），每人完成 6 个真实业务任务（查达人报价、组合推荐、查商单状态、建方案走审批、记录跟进、结案沉淀），任务顺序随机化避免学习效应。

| 观测项 | 定义 | 目标值 |
|---|---|---|
| 任务完成率 | 不需要外部帮助独立完成的任务比例 | ≥ 80% |
| 单任务用时 | 从看到任务到确认完成的中位数 | ≤ 3 分钟（对照人工翻台账的基线用时，预期缩短 50% 以上） |
| 追问次数 | 同一任务中用户需要重新表述问题的次数 | ≤ 1 次 |
| 纠错接受率 | 用户指出回答错误后，重新提问得到正确结果的比例 | ≥ 90% |

### 4.2 问卷量表

- **SUS 系统可用性量表（System Usability Scale，10 题标准量表）**：目标 ≥ 70 分（业界「良好」线为 68）；
- 附加三题（1–5 分）：回答可信度 / 再用意愿 / 推荐意愿，目标均值 ≥ 3.8。

### 4.3 线上行为埋点（长期持续运行）

| 埋点 | 定义 | 监控目标 |
|---|---|---|
| 会话完成率 | 会话中至少完成一次业务动作（工具写操作或获得明确答案）的比例 | ≥ 70% |
| 工具调用成功率 | 工具执行无异常返回的比例 | ≥ 98% |
| 拒答率 | 回答「未找到依据」的比例，按问题分层监控 | 波动超过基线 5 个百分点时告警（可能意味着语料覆盖缺口或管线退化） |
| 人工纠正率 | 用户明确否定回答后重新提问的比例 | ≤ 10% |
| 会话满意度 | 会话结束后的两档评价（有帮助 / 没帮助） | 「有帮助」占比 ≥ 75% |

### 4.4 前后对比设计

不追求严格的 A/B 分流（单机部署、用户量小，分流统计功效不足）；采用**前后对照 + 基线锚定**：每次重大变更（管线参数、语料版本、模型版本）前后各跑一轮同一评测集与同一任务清单，差异归因到变更内容；人工基线（纯手工翻台账做同样任务）在项目首次实测时测一次，作为长期对照锚点。

## 五、性能与质量保障（生产口径）

### 5.1 延迟指标（按分位数定义）

| 指标 | 定义 | 目标值 | 依据 |
|---|---|---|---|
| 首字延迟 P50 / P95 | 从用户发送到第一个字到达浏览器的中位数 / 95 分位（对话已流式化，首个 token 到达即视为响应开始） | P50 ≤ 3 秒 / P95 ≤ 8 秒 | 已实现真流式输出后寒暄类热态首字实测 1.3–2.2 秒，P50 目标留有余量；P95 覆盖冷启动与网络抖动 |
| 检索延迟 P95 | 单次检索（向量 + 关键词 + 融合 + 重排序）的 95 分位 | ≤ 1.5 秒 | 云端重排序 35 毫秒/条 × 10 候选 + 向量检索百毫秒级，主要耗时在重排序网络往返 |
| 完整回答延迟 P95 | 多工具链问答从发送到回答完成 | ≤ 45 秒 | 复杂问题需 2–4 次工具调用串行执行，受大语言模型生成速度主导 |
| 吞吐 | 单实例并发处理中的会话数 | ≥ 10 会话 | 受大语言模型服务端配额限制为主，应用层异步框架（FastAPI 异步接口）不构成瓶颈 |

**测量纪律**：延迟数字必须标注「冷启动 / 热态」与并发背景（空载 or 有并发）；禁止用单次最佳值代表服务水平。

### 5.2 质量回归门禁

| 触发条件 | 必须执行 | 门禁 |
|---|---|---|
| 语料变更（新增/删除/重切片） | 检索评测集全量 + 消融 ①⑤⑦ 组 | Hit@1 下降超过 0.03 时禁止发布，归因后修复 |
| 管线参数变更（融合权重/去重上限/候选数） | 同上，并列变更前后数字 | 任一分层指标下降超过 0.05 需人工评审 |
| 模型版本变更（对话模型/Embedding 模型） | 全部 8 组消融 + RAGAS 30 条抽样 + 工具调用 50 条 | 全部合格线通过才发布 |
| 每周例行 | 消融 ①⑤⑦ + RAGAS 抽 10 条 | 指标漂移告警 |

### 5.3 评测自动化

- 评测脚本统一入口（检索评测 / 生成评测 / 工具调用评测各一个命令），结果落盘 JSON 与 Markdown 报告，报告自动带语料版本、评测集版本、运行日期；
- 首字延迟用服务端推送事件流的事件时间戳在真实链路中测量（不压测裸模型接口），报告同时记录冷启动首轮数据；
- 评测运行历史保留完整，任何历史报告可回溯。

## 六、实施优先级

| 阶段 | 内容 | 依据 |
|---|---|---|
| 立即 | 评测集 150 条构建（1.1–1.3）+ 检索五指标 + 消融 ①⑤⑦ | 评测集是一切的地基；哨兵组最廉价且最能抓退化 |
| 短期 | 消融全 8 组 + RAGAS 30 条 + 业务规则校验（数值/拒答） | 补齐生成层与归因能力 |
| 中期 | 工具调用 50 条用例 + 线上埋点 | Agent 行为与线上表现 |
| 长期 | 用户实测（5–8 人任务式）+ SUS 量表 | 真实用户反馈，成本最高放最后 |
