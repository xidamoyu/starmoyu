> 用途：投递大模型应用开发岗位（检索增强生成 / 智能体方向）时的项目描述底稿。

## 一、一句话版本

基于 LangGraph 框架的对话式商单业务助手：大语言模型自主调用 19 个工具，完成「达人筛选 → 方案生成 → 审批流转 → 跟进记录 → 结案复盘 → 经验沉淀回流知识库」的完整业务闭环；配合向量与关键词混合检索、交叉编码器重排序、以及「预览 + 两次确认」的经验沉淀协议，端到端回归测试 36 项断言全部通过。

## 二、简历项目描述（可直接粘贴）

**项目名称**：MCN 商单资产智能助手（个人全栈项目，2026 年 9 月至今）

**技术栈**：LangGraph · LangChain · FastAPI · Vue3 · PostgreSQL · Milvus · MinIO · qwen3.8 / qwen-vl · BGE 向量模型 · BM25 · CrossEncoder

1. **对话式智能体主链路**：使用 LangGraph 的 StateGraph 组织节点，通过 `bind_tools` 把 19 个工具的函数签名与说明文档交给大语言模型，由模型自主决定调用哪个工具、调用几次、何时结束；工具执行结果回喂给模型形成多轮循环。后端 FastAPI 提供 41 个接口（登录鉴权用 JSON Web Token，对话用服务端推送事件流），前端 Vue3，PostgreSQL 共 14 张表。

2. **混合检索链路**：非结构化语料（结案案例、在途跟踪单、刊例报价表、平台规则、方法论，共 2086 个文本块）走「向量召回 + BM25 关键词召回 → 倒数排名融合 → 文档级去重 → CrossEncoder 重排序」的完整管线；结构化数据（14289 个达人、400 个商单）走 SQL 精确过滤（类目、粉丝量级、报价上限、排他期），由大语言模型根据用户问题自主决定查哪一路。评测结果：完整链路 Hit@1 为 0.694、MRR 为 0.788，相比纯向量检索基线分别提升 0.143 和 0.126（统计口径：语料 2063 块、评测集 98 条，评测集与语料同源反向生成）。

3. **生成质量评测**：用 RAGAS 框架对 20 条真实查询做四项指标评测——忠实度（faithfulness）0.959，说明生成层几乎不编造内容；答案相关性（answer_relevancy）0.794；上下文精确率（context_precision）0.705；上下文召回率（context_recall）0.559。低分项逐条归因为列表型回答的向量相似度天然偏低，不是幻觉问题。

4. **知识回流飞轮（本项目的核心差异化设计）**：商单结案后，智能体主动提醒沉淀经验 → 生成案例预览（自动提炼跟进流水中的复盘结论）→ 用户两次确认 → 案例文本切片后增量嵌入回流 Milvus（按来源文件做幂等，重复入库总块数不变）→ 沉淀的案例可被后续的达人推荐决策召回。效果是语料随业务运转自动增厚，沉淀越多推荐越准。

5. **首响性能优化（流式输出改造）**：定位到改造前的瓶颈——LangGraph 的 updates 流模式要等模型把整段回答生成完才返回第一个字，用户面对 14.5 秒的空白等待。改造为双模式流式：messages 模式把大语言模型的增量文本逐帧推送到浏览器（打字机效果），updates 模式只负责工具调用事件；同时为寒暄类输入设置轻量通道（关闭思考链、不挂载 24KB 的工具定义），实测同一条消息的生成耗时从 3.6 秒降到 1.2 秒。最终实测：寒暄类问题首字时间从 14.5 秒降到热态 1.3 至 2.2 秒（用服务端推送事件流计时脚本落盘存证）；业务类问题保留完整推理链不牺牲正确性。

6. **多模态附件链路**：用户把微信谈判截图拖入对话框 → 视觉模型 qwen-vl-plus 完整转写图中对话（实测主对话模型是纯文本模型，图片地址会被静默丢弃，视觉必须独立通道）→ 智能体从转写内容抽取合作特质（付款要求、排期习惯、沟通偏好，附原文引用）→ 确认卡用户确认后入库；原图存 MinIO 对象存储留档可溯源。

7. **数据入口双重防线**：达人库、商单台账、非结构化文档三类数据统一进入暂存区，由大语言模型做质检预审（实测抓出预算为负数 20000 元的脏数据并判拒绝）→ 管理员确认或驳回后才写正式表；非结构化文档确认后立即向量化、即时可检索。

8. **权限与审计**：三级角色（管理员 / 运营 / 只读），管理员专属用户管理界面；商单字段变更走审批流——智能体无权直接修改预算等资产字段，只能创建变更申请（自动捕获旧值快照），审批中心人工批准后由服务层原子写回并留痕。

9. **工程化验证**：14 个业务流程、36 项断言的端到端回归脚本全绿（覆盖简报、检索、方案、审批、跟进、沉淀、结案、案例回流、变更审批、数据清理还原）；每个里程碑有独立验收脚本。

## 三、面试展开点（按追问深度备料）

### 展开点 1：为什么是「真智能体」而不是固定流程编排

- 早期版本是固定路由流水线（规则分类加固定路径），用户一句混合意图（「顺便记个跟进」）就无法处理。重建后的核心区别是：**工具选择的决策权交给大语言模型**。
- 但写数据库的权力收归服务层：大语言模型只能通过工具函数间接触发写库，状态机校验（草稿 → 提交 → 待审批 → 批准）、主键生成、留痕逻辑只写一处。模型幻觉或参数错误污染不了数据。
- 确定性入口兜底：结案表单、审批推进同时提供用户界面上的确定性按钮，智能体路径和界面路径最终走同一个服务层函数。

### 展开点 2：检索为什么这么设计（被追问检索细节时）

- 结构化查询（「找美妆类目粉丝十万以内报价五万以下的达人」）是精确过滤问题，SQL 是唯一正解，向量检索在这类问题上既慢又不准；语义召回问题（「我们做过哪些母婴成功案例」）SQL 写不出来。两路由大语言模型按问题自主路由，工具的说明文档里写清楚「什么情况该调我」。
- **同构文档淹没问题的定位与修复**：评测发现刊例类问题的命中率异常偏低。打印两路检索各自的排名后发现，某份美妆刊例在向量路排第 1、融合后跌到第 15——数十份结构相似的在途跟踪单以数量优势主导了融合分数。修复方案是按文档编号限流（每篇文档最多保留 2 个块）。
- 这个限流组件本身还修过一次更深的缺陷：限流最初作用在融合前的两路列表上（直接丢弃超限块），反而污染了融合分数让正确文档沉底，消融实验某组命中率崩到 0.316；用性能分析工具抓调用栈加单块级追踪定位后，把限流移到融合后的候选池里做（保序、溢出移队尾不丢弃），该组恢复到 0.740。**教训：组件在管线中的位置比组件参数的影响大得多。**
- 重排序模型选型实测决策：本地交叉编码器在 CPU 上 1126 毫秒每条 → 换到 4GB 显存的 GPU 上反而 3225 毫秒每条（显存颠簸，传输瓶颈）→ 云端重排序服务 35 毫秒每条（快 32 倍），同时移除了 3.9GB 的 torch 依赖。用数据否掉了「看似更专业」的方案。
- 候选裁剪参数在三轮不同语料上结论各不相同（一轮有利、一轮有损、终轮持平略优），最终采用裁剪方案并省 15% 耗时——**优化结论是和数据相关的，每次换语料必须重新测量**。

### 展开点 3：首响优化的完整因果链（被追问性能时）

1. **痛点定位**：改造前的对话接口虽然名义上是流式，实际用的是 LangGraph 的 updates 模式——智能体节点内部要等模型把思考链和全文全部生成完才返回，用户等 14.5 秒才一次性看到全文。
2. **改造一（真流式）**：改为同时订阅 messages 和 updates 两种流事件——messages 模式把模型的增量文本块逐帧转发给前端；updates 模式只提取工具调用和工具结果事件。updates 里的完整回答不再重复推送；模型不支持增量时兜底补发全文。前端本来就是累加文本的写法，零前端改动兼容。
3. **改造二（寒暄轻通道）**：命中白名单（你好、你是谁、谢谢等，不超过 14 字且不含任何业务关键词）且当前会话没有关联商单、没有工具调用历史时，切换到关闭思考链且不挂载工具定义的轻量模型实例。判定标准保守：只要带业务词一律走完整通道，宁可慢也不漏调工具。
4. **过程中发现并修复的真实缺陷**：对话入口把用户消息以元组形式传入状态，LangGraph 状态里存的不是消息对象而是裸元组，路由判定读不到内容、恒走完整通道。通过给节点函数加探针逐层打印消息类型定位，统一在两个入口把元组转成 HumanMessage 对象后修复。
5. **量化结果**：寒暄类热态首字 1.3 至 2.2 秒（冷启动首轮 8.6 秒也如实记录在报告中）；测量脚本用服务端推送事件流的事件时间戳计时，报告落盘在 `docs/延迟实测报告-R12.md`。

### 展开点 4：防幻觉的四层防线

1. **检索层**：混合召回加重排序，上下文质量是前提；
2. **提示层**：要求模型数值必须原样引用检索内容、检索不到就明确回答「未找到依据」、用标签隔离检索内容与用户输入；
3. **校验层**：代码级引用越界检测，「参考来源」列表由代码确定性渲染而不是模型生成；
4. **评测层**：RAGAS 忠实度 0.959 实测背书，不靠口头承诺。

### 展开点 5：数据不撒谎的纪律（展示工程素养）

- 所有数字可以复现：接口数用装饰器计数、工具数导入模块后取长度、语料量数据库计数、延迟用事件流时间戳脚本测量；
- 数字过时立即标注时点（例如「2026 年 9 月 29 日实测」），旧值勘误保留在文档里可追溯；
- 踩过的坑全部归档：推理链吃光输出配额导致回复为空、图片地址被纯文本模型静默丢弃、前端驼峰命名与后端下划线命名的字段契约不一致导致校验失败、Windows 子系统闲置 15 秒自动休眠导致向量库端口失联（用保活窗口根治）、校验错误详情数组被渲染成对象字符串等。

### 展开点 6：真实数据清洗踩的坑（体现数据工程能力）

- **多子表纵向拼接**：一个工作表里有 5 段列结构不同的子表，固定列映射必然出错——写了位置感知解析器，按单元格特征（粉丝数、价格、类目白名单）逐行重新定位，错位的 6789 行全部纠正；
- **空值字符串陷阱**：空单元格经过字符串转换变成 "None" 文本入库 9338 条脏数据——建立统一清洗函数防线；
- **数据脱敏**：手机号只保留前 3 位和后 4 位、微信号做不可逆哈希；
- **分成编码语义化**：内部编码 828、837 等还原为折扣率与分成比例的组合再落库。

## 六、已知边界（主动交代比被问倒强）

1. **工具服从性偶发波动**：qwen3.8-flash 模型偶尔对确认类输入不直接调用预期工具（复现率低）。短期靠工具说明强化缓解，明确的改进路径是在状态图里对确认词做确定性分发，不依赖模型自觉。
2. **消融指标时点**：检索指标在语料 2063 块时点实测，语料现已增至 2086 块，指标待下次刷新；引用时必须带口径。
3. **评测集同源风险**：评测集与语料同源反向生成存在偏乐观的可能；缓解方式是评测集动态反查当前数据库，语料一变评测集跟着重建，不做一次性手工题库。
4. **部署形态**：单机部署——PostgreSQL 与 MinIO 在本机 Windows，Milvus 在 Windows 子系统（WSL2）的 Docker 中；未上容器编排。曾实测出子系统闲置自动休眠导致端口失联的问题，用启动脚本里的常驻保活窗口根治。
5. **数据构成三层口径（如实说明）**：达人库 14289 条来自真实业务 Excel 清洗重灌（含脱敏）；商单 400 单与甲方 100 家按真实业务规则构造（预算等于达人单价上限、千次播放成本锚定行业区间），不是随机造数——涉密真实商单本就无法外流，用真实规则仿真是该场景的标准做法；结案案例由数据库内的结案指标确定性渲染生成（不是大语言模型生成），文档与台账天然一致、引用可验证。
