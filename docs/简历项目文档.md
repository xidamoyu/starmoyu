## 版本一：30 秒开场（自我介绍里带过项目）

我最近做完一个个人全栈项目，叫 MCN 商单资产智能助手。简单说就是一个对话式的业务助手：用户用自然语言提需求，大模型自己决定调哪个工具，把达人筛选、方案生成、审批流转、结案复盘这一整条业务闭环跑下来。技术上是 LangGraph 加 FastAPI 加 Vue3，检索这块是 Milvus 向量库加 BM25 的混合检索。这个项目我特意做了一套独立的评测体系，一百零七道测试题，检索和生成质量都实测过，五项检索指标全部达标，等下可以展开讲。

## 版本二：2 分钟完整版（面试官说"介绍一下你的项目"）

这个项目是一个面向 MCN 商单业务的对话式智能助手。我做它是因为我之前在 MCN 行业做过达人和商务对接，很清楚业务里真实的痛点：筛达人、估报价、查案例，全靠人在几张表里翻。

架构上，后端 FastAPI 四十一个接口，前端 Vue3，数据库 PostgreSQL 十四张表，向量库 Milvus，对象存储 MinIO。核心是一个基于 LangGraph 的智能体：我把十九个工具的函数签名和说明交给大模型，由它自主决定调哪个工具、调几次、什么时候结束，工具结果回喂给它形成多轮循环。比如用户问"母婴品牌三十万预算投小红书，有类似商单参考吗"，模型会自己去查在途跟踪单、再检索历史结案案例，最后带着引用编号回答。

检索这块我做得比较扎实。语料是两千零八十六个文本块，走向量召回加关键词召回，倒数排名融合，再经过文档级去重和云端重排序模型。结构化的达人数据和商单台账走 SQL 精确过滤，两条路由由模型自己选。

最重要的是我给它配了独立评估。一百零七道测试题分四层难度，和语料完全解耦出题，避免"从语料抄答案再问语料"的自证偏乐观。实测下来，完整管线的第一条命中率零点七五，前五条命中零点九一，五项指标全部过设计目标线。生成质量用的是检索增强生成评估框架，判分模型和生成模型不同源，忠实度零点九四五，数值保真百分之百——回答里出现的每个数字都能在引用的原文里找到。

这个项目还跑通了一个闭环：商单结案之后，智能体主动提醒你沉淀复盘，确认后经验切片回流向量库，下次做同类决策时能被检索到，语料随业务运转自动变厚。

## 版本三：分段展开稿（面试官往深处问时，按话题取用）

### 讲智能体设计

智能体这块我的核心选择是真自主而不是流程编排。我没有写"先查 A 再查 B"的固定剧本，而是把十九个工具绑给模型，由它自己规划。为了防止失控，我设了步数上限，并且给检索工具补了按名字模糊匹配的参数——早期版本里模型想找某个达人但工具不支持按名字查，它就会换类目反复盲扫十几轮，加了名字参数之后同类问题两步就收敛。这个教训让我明白：工具接口设计直接决定智能体的行为上限。

### 讲检索管线和消融

检索管线里每个组件我都是用消融实验验证过价值的，五组对照：纯向量、纯关键词、融合、加去重、完整管线。两个结论值得一提。第一，融合的价值在召回率：纯向量前十条召回零点八三五，融合后零点九二，因为关键词路在多约束的聚合题上严重退化，两条路刚好互补。第二，重排序的效果是分层的：在精确查找类问题上它把第一条命中率推到零点九三八、前五条百分百命中，但在归纳推理类问题上增益有限，因为重排模型会被结构相似文档里的字面相似片段带偏。所以我的结论不是"组件堆得越多越好"，而是重排序应该按查询类型路由，这个改进方向我在报告里如实写了。

### 讲生成质量评估

生成质量我用检索增强生成评估框架测了四个指标，这里我特别强调判分的独立性：判分模型和生成模型必须不同源，否则模型给自己打分会有自我偏好。忠实度实测零点九四五，达标了，但我没有停在分数上，而是把失分的论断逐条人工归因，分三类：真实的编造、判分口径过严、评测脚本自身的伪影。结果发现剩下的失分里约一半是模型在归纳题里把跟踪单字段当成已核实事实来复述，这就把一个模糊的"分数不够高"变成了一个可执行的改进项：在提示词里强约束归纳性表述的引用边界。

另外数值保真是百分之百：回答引用块里的每个数字我都用脚本和数据库原值做了归一化比对，零偏差。这个校验规则本身也迭代过一版——第一版把商单编号当成数值误报了，修正成只在引用块内比对、排除编号类标识符，规则演进全程留痕。

### 讲性能优化

有个很典型的性能问题：项目早期用户发一句话，要等十四秒半才看到第一个字。排查下来根因不在模型，而在流式模式——原来的配置是整段回答生成完才一次性返回。我改成双通道流式：文本增量逐帧推给浏览器做打字机效果，工具调用事件单独走一路；另外给寒暄类输入加了条轻量通道，关闭思考链、不挂载工具定义。实测寒暄类首字延迟从十四秒半降到热态一点三到两点二秒，业务问题保留完整推理链不受影响。

### 讲数据可信与权限

因为商单数据是要拿来做决策的，我做了几层防线。数据入口：三类外部数据先进暂存区，大模型质检预审加管理员双重确认才落正式表，实测抓出过负预算的脏数据。字段变更：智能体只能创建变更申请，自动捕获旧值快照，人工批准后服务层原子写回并留痕。角色分管理员、运营、只读三级。识图走独立的视觉模型，微信谈判截图能完整转写并抽取合作特质，原图进对象存储留档。

## 版本四：主动交代边界（面试官问"这项目有什么不足"）

我主动说三个不足。第一，语义改写层是检索短板：口语化问法和文档书面语之间有词汇鸿沟，这一层第一条命中率零点六五，明显低于精确查找层的零点九三八，下一步做查询改写。第二，重排序对归纳类问题的增益有限，按查询类型路由的方案我论证了但还没实施。第三，忠实度失分里约一半是归纳性超推，提示词强约束列为行动项。我觉得一个项目的评估报告能把短板定位到这个粒度，本身就说明评测体系是真的在跑、不是摆设。

## 高频追问快答

**问：为什么用 LangGraph 不自己写循环？**
答：我需要的是状态图、断点续跑和步数控制这些骨架能力，LangGraph 的 StateGraph 和检查点正好提供；核心的自主决策还是靠工具绑定加模型自己完成，框架没有替我做业务编排。

**问：为什么向量库选 Milvus？**
答：语料会随沉淀闭环持续增长，需要独立的向量服务支持增量写入和按集合管理，Milvus 的删除和重建语义也比插件型方案干净。这个项目里我实际执行过一次全量重建：以关系库为唯一数据源，重建后两侧两千零八十六条零差异，日常已验证幂等回流不增条数。

**问：评测集怎么保证独立？**
答：三条纪律：从业务真实问题视角出题、标注以文档为单位、全部标注经语料存在性校验。绝不允许"从语料里抄一段再问这段"。

**问：评估框架为什么手工实现不用开源框架本体？**
答：我需要精确控制判分输入的完整性和分段方式——框架默认的上下文裁剪会把支持内容截掉，造成忠实度被低估。手工实现让每个论断的判分过程可审计，这也让我能把失分逐条归因。

**问：最难的 bug 是什么？**
答：流式改造那次。表面上"回答慢"，我先用裸调用证明瓶颈不在模型也不在提示词，才定位到流式模式配置上；改完之后又发现路由不生效，最后查到是消息类型在进入图状态时被包装错了。这两步教会我：性能问题先做归因实验再动手，以及链路改造后每一段的数据类型都要验证。
