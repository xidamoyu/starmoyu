## A. 使用说明：这份文档怎么用

| 阶段             | 用哪几节      | 做什么                                  |
| -------------- | --------- | ------------------------------------ |
| **投递前**        | C + D     | 挑一种简历写法（C），按 D 的速览核对自己能否流利讲出每个数字     |
| **面试前 1 天**    | B + D + L | 背熟 2 分钟稿（B），扫一遍一页纸（D），把数字速查表（L）过一遍   |
| **面试前 30 分钟**  | B + L     | 只背口径和主干，不要试图临场记细节                    |
| **被追问技术细节**    | F + G     | 按话题取用；每个亮点都给了「追问预判 + 答法」             |
| **模拟实战演练**     | **O**     | **让朋友按题号随机抽问，出声作答**；含连环追问链、压力质疑、反问环节 |
| **被问「有什么不足」**  | I         | 背熟三个短板 + 对应的改进方案（**只讲不足不给方案是减分项**）   |
| **面试官说「演示一下」** | K         | 按脚本走，不要临场乱点                          |
| **面完复盘**       | G + I     | 记录当场答不上来的点，回来补进 F/G                  |

**一句话原则**：这份文档里的**数字都是真的、口径都能说清**。你要做的是把它们讲成「我知道每个数字是怎么来的」，而不是「我记得住数字」。

## B. 口头稿：30 秒 / 2 分钟 / 5 分钟

> 全部是照念就能说的完整句子。**不要背稿子的语气，背它的结构。**

### B1. 30 秒版（自我介绍里顺带提一句）

> 我上一家公司做的一个全栈 AI 应用项目，叫 Starmoyu，面向 MCN 商单业务的对话式智能助手。  
> 用户用自然语言提需求，大模型自己决定调哪个工具，把「达人筛选 → 方案生成 → 审批流转 → 结案复盘 → 经验沉淀」整条业务闭环跑下来。  
> 技术上是 LangGraph 做智能体编排，FastAPI + Vue3 做前后端，检索是 Milvus 向量库加 BM25 的混合检索。  
> 最关键的是我给它配了一套**独立评估体系**——107 道题的评测集，跟语料解耦出题，检索和生成质量都实测过，指标和口径都能复现。

### B2. 2 分钟版（面试官说「介绍一下你的项目」）——**必须背熟**

> 这个项目叫 Starmoyu，是一个面向 MCN 商单业务的对话式智能助手。  
> 我做它是因为我之前在 MCN 行业做过达人和商务对接，很清楚业务里的真实痛点：筛达人、估报价、查历史案例、跟进商单，全靠人在几张表里翻，而且经验沉淀不下来——换个人接手就重新踩一遍坑。
>
> **架构上**，后端是 FastAPI，四十一个接口；前端 Vue3；关系库 PostgreSQL，十四张表；向量库 Milvus；对象存储 MinIO。  
> 核心是一个基于 LangGraph 的智能体：我把十九个工具的函数签名和说明交给大模型，由它**自主决定**调哪个工具、调几次、什么时候结束，工具结果回喂给它形成多轮循环。比如用户问「母婴品牌三十万预算投小红书，有类似的在途商单可以参考吗」，模型会自己去查在途跟踪单、再检索历史结案案例，最后带引用编号回答。
>
> **检索这块**是重点。语料两千零八十六个文本块，走「向量召回 + 关键词召回」两条路，用倒数排名融合，再过文档级去重和云端重排序模型。结构化的达人数据和商单台账走 SQL 精确过滤——**两条路由由模型自己选**，因为精确过滤问题 SQL 是唯一正解，语义召回问题 SQL 写不出来。
>
> **最重要的是我给它配了独立评估**。一百零七道测试题，分四层难度，**与语料解耦出题**，避免「从语料抄一段再问这段」的自证偏乐观。实测完整管线第一条命中率 0.750、前五条 0.913，五项指标全部过设计目标线。生成质量用了 RAGAS 框架，判分模型和生成模型**刻意不同源**，忠实度 0.945，数值保真 100%——回答引用块里的每个数字都能在原文里找到。
>
> 另外这个项目跑通了一个**数据飞轮**：商单结案后智能体主动提醒沉淀复盘，用户两次确认后，案例切片自动增量回流向量库，下次做同类决策能被检索到——**语料随业务运转自动变厚，沉淀越多推荐越准**。
>
> 我还做了一次**推倒重建**：第一版是固定流水线的 RAG demo，多轮对话、真工具调用、写回闭环全缺，我自己判定不合格，重构成了现在这个真 Agent 版本。

## C. 简历条目：三种写法，直接粘贴

> 每条都控制在 A4 纸 3-5 行的密度。**选一种，不要混着用**；投不同岗位换不同写法。

### C1. 写法一：大模型应用开发岗（推荐主投）

**Starmoyu · MCN 商单资产智能助手**（公司内部系统 · 工作经历）  
`LangGraph Agent · RAG · Milvus · PostgreSQL · FastAPI · Vue3 · Qwen`

- 构建对话式智能体业务系统：LangGraph `bind_tools` + ToolNode **真 Agent 循环**（LLM 自主选工具、结果回喂、多轮迭代），**19 个工具**覆盖「达人筛选→方案生成→审批流转→跟进记录→结案复盘→经验沉淀」商单全生命周期；FastAPI(JWT/SSE) + Vue3 前端，**41 个 API 端点、14 张 PG 表、服务层唯一写库**
- 设计**混合检索管线**：Milvus 向量（bge-m3 1024 维）∥ BM25（jieba 分词）→ 元数据预过滤 → RRF 融合 → 文档类型先验 + 配额 → 文档级去重 → 云端 Rerank 精排；语料 **2086 块**，**107 题**分层评测集（与语料解耦），五组消融隔离每个组件贡献
- **独立评估体系**（本项目最大差异化）：检索五指标 **Hit@1 0.750 / Hit@5 0.913 / MRR 0.823 / Recall@10 0.918 / NDCG@10 0.843**，五项全部达标；生成层 RAGAS 四指标 + 业务规则校验：**faithfulness 0.945、数值保真 100%（24/24）、拒答正确 100%**，判分模型与生成模型刻意不同源
- **结构化/非结构化双路检索**：14289 条达人档案 + 400 条商单台账走 **SQL 精确过滤**（类目/量级/粉丝/报价/排他期，毫秒级），非结构化语料走向量检索——**由 LLM 在对话中自主决定查哪一路**
- **数据飞轮闭环**：读侧组合建议带历史结案 ROI（`hist_deals`/`avg_roi`）；写侧结案→主动提醒→预览→两次确认→**单文档增量嵌入回流 RAG**（按 source_file 幂等，6 块秒级，不清库不重跑）——沉淀越多，推荐越准
- **首响性能优化**：LangGraph 双模式流式（messages 增量 token 逐帧 + updates 工具事件），寒暄类首字 **14.5s → 热态 1.3-2.2s**（SSE 事件流计时实测）；寒暄走「关思考链 + 不挂工具 schema」轻通道，业务问题保留完整推理链

### C2. 写法二：RAG / 检索算法岗

**Starmoyu · MCN 商单资产智能助手**（公司内部系统 · 工作经历）  
`RAG · 混合检索 · 重排序 · 评测体系`

- 负责**检索管线设计与消融验证**：向量召回（Milvus + bge-m3 1024 维）与 BM25 关键词召回双路并联，RRF 融合后依次叠加元数据预过滤、文档类型先验与配额、文档级去重、Cross-Encoder 云端重排；用 **5 组消融 + 107 题分层评测集**隔离每个组件的真实贡献
- **定位并修复「同构文档淹没」缺陷**：高相关刊例表向量召回排第 1，RRF 融合后跌至第 15——根因是数十份结构相似的跟踪单以数量优势主导融合分数；引入文档级去重修复。**且修过一次真 bug**：去重最初放在融合前的两路列表上会污染 RRF 输入，导致 Hit@1 从 0.633 崩至 0.316，定位后改为融合后「保序 + 溢出移队尾」——**组件在管线中的位置比组件参数影响大得多**
- **重排序增益分层结论**：L1 精确查找层 Hit@1 从 0.875 提升到 0.938（前 5 条命中 1.000），但 L3 多约束聚合层增益有限——重排模型会被同构文档的字面相似片段带偏，据此提出「按查询类型路由重排」的改进方向
- **评测方法论**：评测集与语料解耦（业务视角出题、以文档为单位标注 direct/assist 两档、经语料存在性校验）；RAGAS 四指标手工实现以精确控制判分段，**判分通道与生成通道不同源**避免自我偏好；失分论断逐条二判 + 人工归因
- **重排序选型实测决策**：本地 CrossEncoder CPU 1126ms/条 → GPU fp16 反而 3225ms/条（4GB 显存颠簸）→ 云端 DashScope `gte-rerank-v2` **35ms/条（32×）**，并移除 3.9GB torch 依赖——用数据否掉「看似更专业」的方案

### C3. 写法三：全栈 + AI 应用岗（强调工程落地）

**Starmoyu · MCN 商单资产智能助手**（公司内部系统 · 工作经历）  
`FastAPI · Vue3 · PostgreSQL · Milvus · MinIO · LangGraph`

- **端到端全栈实现（本人负责数据 → 检索 → Agent → 后端 → 前端 → 评测全链路）**：FastAPI（JWT 鉴权 + SSE 流式）41 端点，Vue3 + Vite + TS + Element Plus + Pinia 前端 7 页面，PostgreSQL 14 张表，Milvus 向量库，MinIO 对象存储（原件留档 + 预签名直链），Ollama 本地 Embedding

### C4. 这段经历怎么写：工作经历条目 + 本地复刻的双层口径

> **前提**：这个项目**本来就是在上一家公司做的**，本地是复刻版（用于沉淀方法论、可复现、可演示）。所以它应当写在**工作经历**栏，挂公司名。  
> 本节解决两个问题：① 工作经历怎么写成「组织交付」而不是「独立作品」；② **公司生产系统与本地复刻版的双层口径**怎么讲才不乱。

**一、写在「工作经历」栏（条目模板，按实际填）**

```
XX 公司 ｜ AI 应用开发工程师 ｜ 20XX.XX – 20XX.XX
项目：MCN 商单资产智能助手（公司内部系统）

- 面向 MCN 商单业务的对话式智能助手，覆盖「达人筛选 → 方案生成 → 审批流转 →
  跟进记录 → 结案复盘 → 经验沉淀」全流程；与商务/运营同事协作梳理业务流程，
  把原先靠人工翻表的环节收敛进一次对话
- 技术选型与实现：LangGraph 真 Agent 循环（bind_tools + ToolNode，19 工具）+
  Service 层唯一写库；FastAPI（41 端点 / JWT / SSE）、Vue3（7 页面）、
  PostgreSQL（14 表）、Milvus + BM25 混合检索、MinIO 对象存储
- 负责检索链路设计与调优：混合召回 + RRF 融合 + 文档级去重 + 云端重排；
  语料 2086 块，五组消融隔离组件贡献，完整管线 Hit@1 0.750 / MRR 0.823
- 负责评测体系建设：107 题分层评测集（与语料解耦）、RAGAS 四指标 + 业务规则校验，
  判分模型与生成模型不同源；忠实度 0.945、数值保真 100%
```

**二、工作经历写法 ≠ 个人项目写法（关键区别）**

|    | **工作经历**该突出                             | 个人项目该突出            |
| -- | --------------------------------------- | ------------------ |
| 重心 | **组织约束 + 协作 + 真实用户 + 业务结果**             | 技术广度 + 自驱 + 独立交付   |
| 语言 | 「与商务/运营协作梳理流程」「上线后 N 个同事日常使用」「支撑 X 单/月」 | 「独立完成」「自主设计」       |
| 忌  | 写成「我一个人做的」——**浪费了工作经历这个位置最值钱的部分**       | 写成「团队交付」——会被追问协作细节 |

> 一句话：**工作经历证明的是「你能在真实约束和协作下交付」，这是项目经历替代不了的。所以别把它写成个人作品的语气。**  
> 另：写了协作就要能答出协作细节（谁提的需求、你怎么和运营对齐口径、评审怎么过），这是工作经历条目必然会被追问的地方。

**三、双层口径：公司生产系统 vs 本地复刻版（本节最实用）**

你现在手里有两套东西，讲的时候天然会分叉。**把两条线分清，面试就不会乱：**

| 维度    | 公司生产系统（工作经历那侧）            | 本地复刻版（可展示那侧）           |
| ----- | ------------------------- | ---------------------- |
| 能讲什么  | 业务背景、协作方式、上线状态、真实使用量、业务结果 | **技术细节、代码结构、指标、排查过程**  |
| 能展示什么 | ❌ 代码与数据涉密，不能展示            | ✅ 可以跑 demo / 给仓库 / 讲实现 |
| 数据    | 公司真实业务数据                  | 合成数据 + 脱敏（正好合规）        |
| 指标口径  | 生产环境口径                    | 本地复刻环境的实测口径            |

**讲法（可直接背）**：

> 「这套系统在公司是内部生产系统，代码和数据涉及公司保密，不能直接展示。  
> 所以我在本地复刻了一套**结构等价**的版本用来自证技术细节——用合成数据，按同样的架构和评测方法做的。  
> 我给你的所有指标和排查过程，都能在复刻版上复现；业务背景和上线情况我讲公司那一侧。」

> **这句话是加分项，不是减分项**：它同时展示了 ① 保密意识 ② 工程复现能力（能复刻说明真的吃透了架构）③ 数字可验证。

**四、两个技术性注意事项（不是道德提醒，是技术口径问题）**

1. **指标口径要一致**：简历上写哪个数，讲的时候就给哪个口径。公司生产口径和本地复刻口径**如果不同，要能说清差别**（语料规模、数据来源、并发背景都可能不同）。  
   ⚠️ 最容易被抓的是：把本地复刻的指标当成生产系统指标讲——被追问「这是线上数据吗」就答不上。
2. **仓库里别放公司真实数据**：本地复刻版可以给面试官看，但确认原始 Excel、内部文档这类文件不进 git（这个项目本来就有这条纪律）。

**五、被问「为什么在本地又复刻一套」怎么答**

> 「两个原因。  
> 一是**验证**——我想确认这套架构是真的可复现，而不是跑在公司特定环境里的一次性产物；复刻一遍才算把架构吃透。  
> 二是**沉淀**——公司的代码和数据我不能带走，但方法论和架构我可以带着走。本地这套就是我的技术档案，以后做同类系统能直接复用。  
> 顺带说，复刻过程里我还发现了几个原版没暴露的问题（比如去重组件位置放错导致指标崩），**复刻本身也是一次 code review。**」

**六、被问「你在大模型团队待过吗」怎么答**

> 「我在上一家公司做的是**业务侧的 AI 应用开发**——从需求梳理、Agent 编排、检索管线、后端前端到评测体系是我这条线负责的。我不在专门的大模型算法团队，模型是调云服务 API。  
> 但我做的这部分正好是**应用层落地最难的部分**：工具怎么设计模型才不乱调、检索链路的每个组件贡献多少、怎么证明它没编造。这些我有实测数据和排查过程。」

### F1. 亮点一：真 Agent 循环 vs 固定流水线

**是什么**  
用 LangGraph `StateGraph` 搭 `agent ⇄ tools` 循环：LLM 通过 `bind_tools` 拿到 19 个工具的签名 + docstring，自己输出 `tool_calls`；`ToolNode` 执行后结果回喂，循环直到 LLM 不再调工具。

**为什么这么设计**  
v1 是「三元分类 router + 固定路径」，用户一句「顺便记个跟进」它就处理不了。真 Agent 的本质区别是：**工具选择的决策权交给 LLM**——路由本身变成涌现的，不用穷举分支。

**代码锚点**

| 文件                                | 位置                      | 关键内容                                                                             |
| --------------------------------- | ----------------------- | -------------------------------------------------------------------------------- |
| `src/agent_graph.py`              | `MCAgent._build()`      | `StateGraph(AgentState)` + `add_node("agent"/"tools")` + `add_conditional_edges` |
| `src/agent_graph.py`              | `_agent_node`           | 注入 SYSTEM_PROMPT、选路（寒暄/主通道）                                                      |
| `src/agent_graph.py`              | `_should_continue`      | 有 `tool_calls` → `"tools"`，否则 `END`                                              |
| `src/agent_graph.py`              | `MAX_STEPS = 25`        | `recursion_limit` 兜底防失控（注释记录了 12 会爆的历史）                                          |
| `src/agent_tools.py`              | `AGENT_TOOLS`           | 基座 10 工具                                                                         |
| `src/m4_tools.py` / `m5_tools.py` | `M4_TOOLS` / `M5_TOOLS` | 沉淀 2 + 全周期 7                                                                     |

**证据**

- `verify_m1.py` 8/8：包含「Agent **自主**调 search_kols（LLM 决定，非写死路径）」
- `verify_all` 36/36 全绿

**追问预判**

| 面试官问                          | 怎么答                                                                                                                                                                                                              |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 为什么用 LangGraph 不自己写 while 循环？ | 「我要的是状态图、断点续跑、步数控制这些骨架能力，LangGraph 的 StateGraph + Checkpointer 正好提供。核心的自主决策还是靠 bind_tools + 模型自己完成，框架没替我做业务编排。」                                                                                                  |
| 多轮循环会不会失控？                    | 「两层兜底：一是 `recursion_limit=25`，实测 12 会在复杂连环调用时爆 GraphRecursionError；二是 `handle_tool_errors` 让工具异常变成文本返回给模型，不会中断整轮对话。」                                                                                             |
| 19 个工具会不会太多、模型选不准？            | 「会——所以工具 docstring 我写得很重，每条都写清『何时该调我』。实测过一个反面案例：早期 search_kols 不支持按名字查，模型想找某个达人时会换类目盲扫十几轮，加了 name 模糊匹配参数后同类问题两步收敛。**工具接口设计直接决定智能体的行为上限。**」                                                                       |
| 断点续跑怎么做的？                     | 「Checkpointer 分级：显式参数 > 环境变量 `LANGGRAPH_CHECKPOINT_SQLITE` → SqliteSaver > MemorySaver。`thread_id` 就是会话 ID。早期文档声称『跨进程持久化』但实际是 MemorySaver，我用三个独立进程做了验证脚本把它改成真的 SqliteSaver 并落盘（`demo_cross_process_resume.py`）。」 |

### F2. 亮点二：结构化查询 vs 向量检索的双路设计

**是什么**  
达人 / 商单筛选走 SQL 精确过滤（`search_kols`、`match_kols_for_requirement`），非结构化语料走向量检索（`search_knowledge`）。**走哪路由 LLM 自己判断。**

**为什么这么设计**

- 「类目=美妆 AND 粉丝>10w AND 报价<5w」是**精确过滤问题**，SQL 是唯一正解——向量检索在这类查询上既慢又不准。
- 「我们做过哪些母婴成功案例」是**语义召回问题**，SQL 写不出来。
- 把决策交给 LLM：工具 docstring 写清适用场景，模型按问题自主路由。

**代码锚点**：`src/agent_tools.py` 的 `search_knowledge` / `search_kols` / `match_kols_for_requirement` 三个工具的 docstring。

**追问预判**

| 面试官问         | 怎么答                                                                    |
| ------------ | ---------------------------------------------------------------------- |
| 为什么不全部用向量检索？ | 「精确过滤上向量检索既慢又不准，而且商单业务对『精确』零容忍——预算 20 万和在途阶段这类字段不能靠语义近似。」              |
| 怎么保证模型选对路？   | 「docstring 写清『何时该调我』。这是 Agent 相对固定 pipeline 的优势——路由是涌现的，不用我写 if-else。」 |
| 结构化那条路性能如何？  | 「SQL 毫秒级。达人 14289 条走类目/量级/粉丝/报价/排他期过滤，实测 CPM 和均播能正常读出。」                |

### F3. 亮点三：混合检索管线与八组消融

**是什么（完整链路）**

```
多路召回（Milvus 向量 ∥ BM25 关键词）
  → 元数据预过滤（类目/平台/量级/粉丝区间）
  → RRF 融合（k=60）
  → 文档类型先验 + 配额保底
  → 文档级去重（每文档最多 2 块）
  → 云端 Rerank 精排（gte-rerank-v2）
  → 引用组装（前 5 条 + 4000 字符窗口）
```

**代码锚点**：`src/starmoyu/retriever.py` — `search()` 是主入口，带 9 个消融开关（`use_bm25/use_vector/use_rrf/use_rerank/use_meta_filter/use_prior/use_dedupe/use_quota`）。**所有组件开关都在这一个函数里，消融实验靠切开关，不靠改代码**——这是能做 5 组消融的前提。

**指标（v4 口径：2086 块 / 107 题，检索分母 92 题）**

| 组别          | Hit@1     | Hit@5     | MRR       | Recall@10 | NDCG@10   |
| ----------- | --------- | --------- | --------- | --------- | --------- |
| A1 纯向量      | 0.717     | 0.837     | 0.771     | 0.835     | 0.784     |
| A2 纯 BM25   | 0.620     | 0.837     | 0.708     | 0.853     | 0.756     |
| A3 融合(RRF)  | 0.696     | 0.870     | 0.772     | 0.920     | 0.812     |
| A4 +去重      | 0.696     | 0.870     | 0.772     | 0.920     | 0.812     |
| **A5 完整管线** | **0.750** | **0.913** | **0.823** | **0.918** | **0.843** |

**分层的三条结论（这是最能体现深度的部分）**

1. **融合的价值在召回率**：A3 的 Recall@10 0.920 高于 A1 的 0.835 与 A2 的 0.853。**纯 BM25 在 L3 多约束聚合层严重退化**（Hit@1 仅 0.250）——两路互补是必要性的直接证据。
2. **去重在本轮口径下对排序指标中性**（A4 = A3）：去重收益不体现在直接改变融合排名，而在于**给重排序腾出候选多样性**。
3. **重排序增益分层分化**：L1 精确查找层 Hit@1 从 0.875 → 0.938（前 5 条命中 1.000）；但 L3 层收益有限——重排模型对同构跟踪单的**字面相似片段**（如「报价 ¥58,300」式数字）敏感，会把语义更相关但字面相似度低的候选挤出头部。

**追问预判**

| 面试官问              | 怎么答                                                                                                                                          |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 消融怎么做才可信？         | 「一次性跑在同一评测集、同一语料版本上，每次只开关一个组件。而且**必须输出分层矩阵**——总平均会掩盖弱项：L3 普遍低而 L1 拉高总分，只看总数会误判管线健康。」                                                         |
| 「同构文档淹没」你怎么发现的？   | 见 [G1](#g1-同构文档淹没从-hit1-0633-崩到-0316)。                                                                                                       |
| RRF 的 k 为什么取 60？  | 「沿用业界常用值。更重要的是消融显示融合本身在本语料上的收益主要体现在 Recall@10（0.920 vs 单路 0.835/0.853），不是 Hit@1。」                                                            |
| 为什么重排序增益在 L3 反而低？ | 「重排是 Cross-Encoder，拼 query 和 doc 做 token 级交互，对**字面相似**敏感。L3 多约束聚合题的正确答案往往字面不相似（要靠多文档综合），同构跟踪单里的数字片段反而更像「命中」。诚实结论：重排应该按查询类型路由，这个方向我论证了但还没实施。」 |

### F4. 亮点四：重排序选型的实测决策

**是什么**  
本地 CrossEncoder → GPU → 云端 的三次实测选型。

**数据**

| 方案                           | 延迟                  | 结论                      |
| ---------------------------- | ------------------- | ----------------------- |
| 本地 CrossEncoder（CPU）         | 1126 ms/条           | 太慢                      |
| 本地 GPU fp16                  | **3225 ms/条**（反而更慢） | 4GB 显存颠簸，PCIe 瓶颈，**否决** |
| 云端 DashScope `gte-rerank-v2` | **35 ms/条**         | **采纳（32×）**             |

采纳云端后还移除了 3.9GB 的 torch/transformers 依赖（venv 从 1.3G 降到 660M）。

**追问预判**

| 面试官问          | 怎么答                                                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 为什么 GPU 反而更慢？ | 「GPU 只有 4GB，模型权重加载后在显存里颠簸，加上 CPU-GPU 之间的 PCIe 传输成本，单条前向的开销远超 CPU。**『上 GPU』不是默认更优，要看模型规模和批处理形态**——我这里单条、小模型、无批处理，GPU 反而不划算。」 |
| 云端有网络成本，怎么权衡？ | 「35ms 是实测中位（30 条候选 1051ms），业务可接受。而且省掉了 3.9GB 依赖和本地推理运维。**用数据否掉『看起来更专业』的方案，是这次选型最大的收获。**」                                    |

### F5. 亮点五：独立评估体系（这块最容易被记住）

> **这是整个项目最能拉开差距的部分。很多项目止步于「我做了」，你能回答「我做的好在哪、好在多少、怎么证明」。**

**是什么（四层）**

| 层    | 内容                                                             | 关键设计                                                                 |
| ---- | -------------------------------------------------------------- | -------------------------------------------------------------------- |
| 评测集  | **107 题**（L1 精确查找 32 / L2 语义改写 40 / L3 多约束聚合 20 / L4 否定与边界 15） | **与语料解耦**：业务视角先出题、后标注；以文档为单位标注 direct(1)/assist(0.5) 两档；全部标注经语料存在性校验 |
| 检索评估 | 五指标 + 5 组消融，**必须输出分层矩阵**                                       | 分母只统计 L1-L3 共 92 题；L4 拒答题不进检索分母                                      |
| 生成评估 | RAGAS 四指标 + 业务规则校验，抽样 29 条                                     | **判分模型与生成模型不同源**（qwen-plus 判 qwen3.8-flash）；忠实度**分段判分**              |
| 结果解读 | 失分论断逐条二判 + 人工归因                                                | 19 条未支持论断 → 4 类归因（真实编造 52.6% / 口径过严 21.1% / 评测伪影 21.1% / 截断伪影 5.3%）  |

**指标（v4）**

检索（92 题）：Hit@1 0.750 / Hit@5 0.913 / MRR 0.823 / Recall@10 0.918 / NDCG@10 0.843 —— **五项全达标**  
生成（29 条抽样，n=24）：faithfulness 0.945 ✓ / answer_relevancy 0.856 ✓ / ctx_precision 0.731 ✗ / ctx_recall 0.769 ✓  
业务规则：数值保真 **100%（24/24）** / 拒答正确 **100%（5/5）**

**方法论上最值得讲的三个点**

1. **判分独立性**：「判分模型必须和生成模型不同源，否则模型给自己打分有自我偏好。我用 qwen-plus 判 qwen3.8-flash，温度取 0。」
2. **忠实度分段判分**：「开源框架默认的上下文裁剪会把支持内容截掉，导致忠实度被低估。我手工实现，把回答拆成『结论段 + 依据段』各与完整上下文配对判分，论断级合并——这样每个论断的判分过程可审计，我才能把失分逐条归因。」
3. **失分归因把模糊变可执行**：「19 条失分里约一半是**归纳性超推**——L3 归纳题里模型把在途跟踪单的字段当成已核实事实复述。这就把一个模糊的『分数不够高』变成可执行的改进项：**在提示词里强约束『跟踪单候选/需求描述仅作参考性表述』**。」

**追问预判**

| 面试官问                            | 怎么答                                                                                                                                                  |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 评测集和语料同源会不会偏乐观？                 | 「这是个真问题，我主动交代：**评测集与语料同源生成确实存在系统性偏乐观风险**。我的缓解方式是评测集**动态反查当前库**——语料一变评测集跟着重建，不做一次性手工题库。另外出题纪律是『先出题、后标注』，出题人不得先浏览语料原文再倒推题目。」                           |
| 数值保真 100% 怎么算的？                 | 「代码确定性执行，不依赖判分模型：正则抽取回答**引用块内**的数值，与所引用上下文原文归一化（千分位）后比对；**排除商单编号、年份、纯序号类标识符**。这个规则本身迭代过——第一版把商单编号当数值误报了，修正后限定引用块范围。3 条初检失败逐条核验后均为合法加总或评测伪影，无真实数值编造。」 |

| 为什么不用开源 RAGAS 框架本体？             | 「我需要精确控制判分输入的完整性和分段方式，框架默认裁剪会截掉支持内容。手工实现让每个论断可审计。」                                                                                                   |

### F6. 亮点六：数据飞轮（双向闭环）

**是什么**

- **读侧**：`match_kols_for_requirement` 的组合建议带 `hist_deals`（历史结案单数）+ `avg_roi`（平均 ROI，取自 `deal.result_metrics` 原值）。
- **写侧**：结案 → Agent **主动提醒**沉淀 → 用户同意 → 案例预览（自动提炼跟进流水里的拒绝原因/返点/档期/改稿经验）→ 用户确认（可补充要点）→ **单文档增量嵌入**（按 source_file 先删后插，幂等，6 块秒级，不清库不重跑）→ 知识库即时可检索。

**为什么是最有价值的设计**  
它让系统「会自己变强」：沉淀越多 → match 建议的 avg_roi 越准 → 下单决策越准 → 语料越厚。

**实测**：美妆 10 万预算 → 小美妆记 2 单 avg ROI 1.59 / 是美妆日常 2 单 0.98 / 老美妆说 0 单 null。**沉淀越多建议越准，这个结论有实测支撑。**

**追问预判**

| 面试官问           | 怎么答                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 增量入库怎么保证不重不漏？  | 「按 `source_file` 先删后插，幂等。单测验证过：二次入库总块数稳定（2064），不增条数。只重建 chunk 表 + Milvus，**绝不碰结构表**——v1 的 ingest.py 会 TRUNCATE `kol_profile`，已经弃用了。」 |
| 为什么不直接重新跑全量重建？ | 「全量重建成本高、有风险，而且业务是持续的小增量。单文档增量 6 块秒级完成，不打断在线服务。」                                                                                     |
| 用户不确认会怎样？      | 「**确认前零落库**，这是硬关口。全流程两次确认，且禁止跳过预览直接入库（提示词硬约束 + 验收断言双重把关）。」                                                                           |

### F8. 亮点八：首响性能优化（真流式 + 轻通道）

**是什么**  
① 真流式：`stream_mode=["messages","updates"]` 双模式——messages 推 LLM 增量 token（打字机），updates 推工具事件（工具卡片）。  
② 寒暄轻通道：`_is_chitchat()` 判定短且无业务信号的输入 → 走 `model_light`（`enable_thinking=False` + **不挂 24KB 工具 schema**）。


**数据**

| 场景          | 改造前首字 | 改造后首字                   |
| ----------- | ----- | ----------------------- |
| 寒暄「你好」      | 14.5s | **热态 1.3 / 1.9 / 2.2s** |
| 能力自述「你能干什么」 | —     | 1.2s                    |

**排查故事**（这个能讲成完整的 debug 故事）  
「项目早期用户发一句话要等 14 秒半才看到第一个字。排查下来**根因不在模型也不在提示词**——我用裸调用证明模型本身很快，才定位到是**流式模式配置**：原来用的是 updates 模式，整段回答生成完才一次性返回。改成双通道流式后，又发现路由不生效，最后查到是**消息类型在进入图状态时被包装错了**。这两步教会我：性能问题先做归因实验再动手，以及链路改造后每一段的数据类型都要验证。」

**追问预判**

| 面试官问          | 怎么答                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------ |
| 为什么寒暄要走轻通道？   | 「寒暄不需要推理也不需要工具，但主模型每次都要加载 24KB 工具 schema 并跑思考链。关掉这两项，同消息首字从 3.6s 降到 1.2s。**快慢分离，业务问题保留完整推理链，不牺牲正确性。**」 |

| 冷启动为什么是 8.6s？ | 「首轮含服务冷启动。热态复测才是 1.3-2.2s，**口径要说清冷热态**，不能说『首字 1.3 秒』。」                                                 |

## G. 故事库：可讲 8 个的技术难点与真实 bug

> 面试官最爱问「你遇到过最难的问题是什么」。**准备 8 个，按对方提问方向挑一个讲**。每个都按「现象 → 排查 → 根因 → 修复 → 教训」组织。

---

### G1. 「同构文档淹没」：从 Hit@1 0.633 崩到 0.316

**现象**：刊例类问题 Hit@5 异常低。高相关的美妆刊例表在向量召回排第 1，**RRF 融合后跌到第 15**。  
**排查**：打印向量路与 BM25 路的**各路排名**，发现 45 份结构相似的跟踪单在两路都大量上榜，`1/(k+rank)` 累加后数量优势盖过单篇高相关。  
**修复（第一次）**：按 doc_id 限流（每文档最多 2 块）——但这里埋了第二个坑。  
**新问题**：限流最初作用在 **RRF 融合前的两路列表**上（丢弃超限块），**污染了融合分**，正确文档整体沉底，消融③组 Hit@1 崩到 0.316。  
**修复（第二次）**：用单例块级追踪定位后，把去重**移到融合后的候选池**做「保序 + 溢出移队尾（不丢弃，rerank 仍可见）」→ Hit@1 恢复 0.740。  
**教训**：**组件在管线中的位置比组件参数影响大得多。** 这句话可以直接说。

---

### G2. `max_tokens=2500` 被 reasoning 吃光

**现象**：结案复盘流时灵时不灵，模型不调工具、返回空内容。  
**排查**：查 `finish_reason` 发现是 `length`——思考链把 token 预算吃光了，正文没生成，工具自然没调。  
**根因**：此前一直以为是「LLM 服从性波动」，**其实这是真根因之一**。  
**修复**：max_tokens 提到 8000，确认流随即稳定。  
**教训**：**「模型不听话」这个模糊归因，掩盖了一个具体的工程配置问题。遇到模型行为异常，先查 finish_reason 和 token 用量，别急着怪模型。**

---

### G3. 真实 Excel 的三个脏数据坑

1. **多子表纵向拼接**：一个 sheet 里 5 段不同列结构的子表，固定列映射必错。写了**位置感知解析器**，按单元格特征逐行重定位（粉丝/价格/类目白名单判断），**错位行 6789 → 0**。
2. **`str(None)` 陷阱**：空单元格经 `str()` 变成 `"None"` 字符串入库，产生了 **9338 条脏流水**。统一 `clean_str()` 防线。
3. **psycopg `%` 格式符**：SQL 内联 `CURRENT_DATE-%s+%s` 时，`%s` 被当格式符，占位符反复错位。一律纯 `%s` 参数 + Python date 对象。

**教训**：真实数据比仿真数据脏得多，**每一条清洗规则都是被真实脏数据逼出来的**。

---

### G4. 视觉通道：主模型对 `image_url` 静默丢弃

**现象**：用户拖入微信谈判截图，期望抽取出合作经验，但模型说「无法识别」。  
**排查**：实测发现带的图 prompt_tokens **只增加 104** —— 说明 `image_url` 被**静默丢弃**了。主对话模型（`deepseek-v4-flash`）是纯文本模型。  
**修复**：新增 `llm.chat_vision()`，视觉必须走 **qwen-vl-plus**（DashScope 视觉通道）。实测 760×1400 的截图能准确读出「8万8/预付50%/10月22日20点」。  
**连带 bug**：`chat_stream` 原本传的是 `body.text`，**转写结果根本没进 Agent 输入**——修了才算真通。  
**教训**：**接口「接受」参数不等于「使用」参数。** 静默丢弃是最难查的一类 bug，要用可观测的指标（token 用量）来证明。

---

### G5. 流式改造：从「回答慢」到路由不生效

**现象**：用户发一句话要等 14.5s 才见到第一个字。  
**排查**：先用**裸调用**证明瓶颈不在模型、不在提示词 → 定位到流式模式配置（updates 模式整段生成完才返回）。  
**修复后新问题**：改成双通道流式后路由不生效。  
**根因**：**消息类型在进入图状态时被包装错了**。  
**教训**：性能问题**先做归因实验再动手**；链路改造后**每一段的数据类型都要验证**。

---

### G6. 沉淀流的「LLM 服从性」问题

**现象**：用户确认后模型只做口头总结、不入库；或者一步到位不等确认；或者反问商单号打断流程。  
**排查**：这不是模型能力问题，是**工具粒度**问题——两步工具（record → confirm）给了模型跳步的空间。  
**修复**：合并为**单原子工具** + 把确认关口移到对话层（提示词硬约束）+ 验收断言双重把关。另加参数容错（kol_id/kol_name 二选一、中英文键名都认、list/str 都收）。  
**诚实声明**：LLM 服从性**不是 100%**（出现过确认后不入库的波动）。通过提示词强化 + 单工具原子化提升到**连续 3 轮稳定**；要 100% 确定性可把待确认数据放 LangGraph state 做确定性分发（记为 TODO）。  
**教训**：**别用提示词解决结构问题。能用工具粒度/结构约束解决的，不要靠「求模型听话」。**

---

### G7. 召回失败：数据在 PG 不在向量库

**现象**：用户实测发现「谈到达人时召回不出沉淀经验」。  
**排查**：Agent 跳过 `list_kol_traits` 直接搜知识库——**但特质数据在 PostgreSQL，不在向量库**，当然搜不到。  
**修复**：提示词强制化（该工具前加【强制】标注，写明「禁止跳过该工具直接回答」）+ 昵称歧义时返回候选列表强制澄清。  
**教训**：**存储位置决定了必须走哪条检索路径，这一点要在提示词里显式说清，不能指望模型自己推断。**

---

### G8. 文档与代码漂移（第三方审计暴露的问题）

**背景**：项目做过一次**独立 reviewer 子代理审计**（68 次工具调用 / 26 分钟），它自己读源码、跑命令、查数据库，发现了我此前审计**漏掉的 9 处问题**。  
**最危险的一类**：**过期数字复用**——分类型明细取自过期的日志（第⑦组），而当前结论是第⑧组，结果把「MRR 0.224」当成「已知短板」**写进了说明书和简历**，即**基于假数据编出了一段有说服力的叙事**。  
**另一类**：**数字口径算错**——「Rerank 32ms/条」是拿 `1030ms ÷ 32 条` 算的，而实际候选池是 **30 条**，分母用错了。这就是「32ms 这个看起来更漂亮的数字」的来源。  
**建立的防线**：①所有数字必须脚本落盘（`scripts/bench_rerank.py` 取代手工估算）；②引用数字前先确认它属于哪次实验；③描述实现顺序的文字与代码同源；④**写不进日志的因果解释就不写成结论**。  
**教训（最能加分的一句）**：**「未实测数字不是凭空编，而是口径算错后没有回查。所以我现在建立的纪律是：任何数字都要能说出它来自哪次实验、哪个日志文件。」**

## H. 高频问答库（按模块，40 题）

### H1. Agent / 编排（8 题）

1. **为什么用 LangGraph？** → F1 追问预判
2. **bind_tools 和固定流水线的区别？** → 「Chain 是线性数据流；v1 的 router 是三元分类 + 固定路径，用户一句『顺便记个跟进』就处理不了。真 Agent 是**工具选择的决策权交给 LLM**，业务价值是一次对话能自然完成『查达人 → 出方案 → 记跟进 → 提审批』的混合意图。」
3. **19 个工具怎么组织？** → 「10 基座（只读 + 写库 + 查询）+ 2 沉淀 + 7 全生命周期。全部 `bind`——只 bind 基座会让模型对 M4/M5 工具『盲调』，签名不在 schema 里服从性时灵时不灵，这是实测复现过的。」
4. **工具报错会怎样？** → 「`ToolNode(handle_tool_errors=...)` 把异常变成文本返回给模型，模型可以据此调整，不中断对话。」
5. **记忆/上下文怎么管？** → 「Checkpointer 持久化，`thread_id` 是会话 ID。会话层还有「钉住商单」：`PATCH /conversations/{id}/pin`，对话上下文自动携带商单，切会话清钉住防闪现——走 LangGraph `configurable` 而不是 contextvar，因为 **SSE 生成器跨线程上下文不可靠**。」
6. **怎么防止 Agent 跑飞？** → 见 F1 追问预判（recursion_limit + 工具错误兜底 + 写操作过闸门）。
7. **多轮对话的状态怎么设计？** → 「`AgentState` 只有 `messages`，用 `Annotated[list, operator]` 做累加。保持 state 最小化——复杂状态放 Service/PG，不放图内。」
8. **为什么不用 AutoGPT / 多 Agent 编排？** → 「这个场景不需要多 Agent：**单 Agent + 19 工具**已经能覆盖，多 Agent 会引入通信成本和不确定性。取舍原则是『不做为了炫技的架构』。」

### H2. RAG / 检索（10 题）

1. **检索链路完整讲一遍** → E2 + F3
2. **为什么混合检索？** → 「向量擅长语义、BM25 擅长精确词。纯 BM25 在 L3 多约束聚合层 Hit@1 只有 0.250，纯向量 0.600——**两路互补有实测证据**。」
3. **RRF 是什么？为什么用它？** → 「Reciprocal Rank Fusion，把多路排名列表按 `1/(k+rank)` 累加融合。相比分数加权，它只用排名不用分数，**免去了不同检索器分数不可比的问题**。」
4. **元数据预过滤为什么必要？** → 「'美妆腰部达人'这类查询，先按 category/tier/fans 过滤再排序，比纯语义排序准。但有个坑：过滤后剩余不足 3 条就回退到不过滤，防止误杀。」
5. **分块策略？** → 「父子块结构：子块用于检索（细粒度匹配），父块用于生成（完整上下文）。`expand_to_parent` 负责扩展。」
6. **重排序原理？** → 「Bi-Encoder 分别编码 query 和 doc 算余弦（快，可预计算）；Cross-Encoder 拼接后整体过模型做 token 级交互（慢，每候选一次前向）。所以是**粗排取 Top-N → 精排对 N 个细排**。」
7. **候选数怎么定？** → 「实测 GT 文档在候选池 top-5 内命中率 100%，说明大部分候选对最终 Top-K 没贡献却要付重排开销。收窄候选数耗时 -16.6% 精度不降。**但同一参数在三轮语料上结论不同——优化结论是数据相关的，每次换语料必须重测。**」
8. **幻觉怎么防？** → 「四层：①检索层（混合召回 + 重排，context 质量是前提）；②提示层（数值必须原样引用、context 没有就明确拒答、`<context>` 标签隔离）；③校验层（引用越界检测，参考来源由代码确定性渲染）；④评测层（RAGAS faithfulness 0.945 背书，不靠口头承诺）。」
9. **embedding 模型选型？** → 「bge-m3，1024 维，本地 Ollama 部署，**零 API 成本**。中文场景表现好。」
10. **语料怎么切片入库的？** → 「Milvus 存向量 + PG 存元数据/父块，双存储。检索时 Milvus 出 chunk_id，再回 PG 取元数据和父块。**PG 是唯一数据源，Milvus 可从 PG 全量重建**——实测重建后两侧 2086 条零差异。」

### H3. 评测（8 题）

1. **评测集怎么构建？** → F5（三条纪律：先出题后标注 / 双向校验 / 解耦更新）
2. **为什么要分层？** → 「总平均会掩盖弱项：L3 普遍低而 L1 拉高总分。分层矩阵同时是行动指南：L1 低说明管线有结构性缺陷，L2 低说明语义匹配不足，L3 低优先改查询理解。」→ 并用 v4 数据说明：**L2 语义改写层 Hit@1 只有 0.650，是短板**
3. **五指标为什么选这几个？** → 「Hit@1（对话场景用户几乎只看第一条依据）+ Hit@5（前端展示前 5 条）+ MRR（综合分）+ Recall@10（多文档题的召回）+ NDCG@10（两档标注下的排序质量）。」
4. **faithfulness 0.945 说明什么、不说明什么？** → 「说明**生成层几乎不编造**——靠三道防线（数值强制引用 + 无依据拒答 + 引用越界校验），是结构保证不是模型自觉。但**不说明回答准**——相关性是另一回事，而且它不保证检索到的内容本身是对的相关文档（那由检索层人工标注兜底）。」
5. **RAGAS 为什么要手工实现？** → 见 F5 追问预判
6. **工具调用正确性评了吗？** → 「**如实说：还没评**。设计方案里这块是『结构化查询路』的专项评估（路由正确率 / 参数正确率 / 结果正确率），用例集列入下一轮首批任务。当前实测覆盖的是检索与生成链路。」
7. **用户实测做了吗？** → 「**没做**。方案里设计了任务式实测（5-8 人 × 6 个业务任务）和 SUS 量表，但成本最高放在最后。当前是自测 + 自动化验收。」
8. **怎么保证评测可复现？** → 「统一入口脚本，结果落盘 JSON + Markdown，报告自动携带语料版本、评测集版本、运行日期、语料规模口径。历史版本不覆盖。」

## I. 诚实边界：怎么说「不足」才加分

> **原则：主动讲不足 + 必须配改进方案。只讲不足不给方案是减分项，讲不足给方案是加分项。**

### I1. 三个短板（背熟）

| # | 短板                    | 支撑数据                                                | 改进方案                                                  |
| - | --------------------- | --------------------------------------------------- | ----------------------------------------------------- |
| 1 | **L2 语义改写层是检索短板**     | 五组消融中 L2 层 Hit@1 最高只有 **0.650**，显著低于 L1 的 **0.938** | 查询改写（口语 → 书面语归一），列为下一优先级。词法鸿沟：用户问「达人现在什么身价」而文档写「刊例报价」 |
| 2 | **重排序对归纳类问题增益有限**     | L1 层 Hit@1 0.875→0.938，L3 层 0.550→0.650 收益明显更小      | 按查询类型路由重排序，或与融合分数插值。**方案论证了但未实施，如实记录不改动管线**           |
| 3 | **归纳性超推**（忠实度的主要失分来源） | 19 条未支持论断中 **10 条（52.6%）是真实编造**，集中在 L3 归纳题          | 提示词强约束「跟踪单候选/需求描述仅作参考性表述」                             |

### I2. 待改进清单（被追问再讲）

- LLM 工具选择**非 100% 服从**——已用 docstring 强化 + 确认卡关口缓解到连续 3 轮稳定；彻底方案是 LangGraph state 确定性分发（**有明确路径，不是悬而未决**）。
- 评测集与语料同源生成存在**偏乐观风险**——缓解方式是评测集**动态反查当前库**，语料一变评测集跟着重建。
- **工具调用用例集未做**、**用户实测未做**、**CI 未接**、**并发压测未做**。
- `context_precision 0.731` 临界未达标——与 4000 字符窗口下多标注题的相关文档配额有关。
- 前端 Markdown 渲染：表格/加粗显示原始语法，影响可读性。
- 拒答校验粒度不足——应细分「完全拒答」与「部分拒答 + 最接近参考」两档。

### I3. 最佳「不足」答法（可直接背）

> 「我主动说三个。**第一**，L2 语义改写层是检索短板——用户口语化问法和文档书面语之间有词汇鸿沟，这一层第一条命中率 0.650，明显低于精确查找层的 0.938，下一步做查询改写。**第二**，重排序对归纳类问题的增益有限，按查询类型路由的方案我论证了但还没实施。**第三**，忠实度失分里约一半是归纳性超推，提示词强约束列为行动项。
>
> 我觉得一个项目的评估报告能把短板定位到这个粒度，本身就说明**评测体系是真的在跑、不是摆设**。」

## O. 模拟面试全真演练（逐题作答稿）

> **与 §H 的区别**：§H 是**速查**（一问一答、简答）；本节是**全真演练**——模拟真实面试节奏，包含**连环追问**、**压力质疑**、**反问环节**。  
> 每题的作答稿是**可照念的自然口语**；灰色旁注是**面试官在考什么 / 陷阱在哪**。
>
> **用法**：让朋友按题号**随机抽问**，你**出声作答**。含追问链的题（O2/O3/O4）必须**连答到底**——真实面试不会给你喘息的间隙。答不出来就是还没准备好。

### O0. 三个万能答题框架（先记这个，比记答案重要）

| 场景      | 框架                    | 一句话口诀                         |
| ------- | --------------------- | ----------------------------- |
| 讲一个技术方案 | **问题 → 方案 → 证据 → 取舍** | 「我遇到什么问题，怎么解决的，怎么证明有效，付了什么代价」 |
| 讲一个不足   | **承认 → 归因 → 方案 → 边界** | 「确实差，因为什么差，打算怎么改，改到什么程度算好」    |
| 被问不懂的   | **明说 + 给路径**          | 「这个我没做过。如果让我做，我会先判断……再动手」     |

> **最容易犯的错**：只讲「方案」，不讲「问题」和「取舍」。面试官想听的是 **你为什么这么选**，不是 **你用了什么**。

### O1. Round 1 · 开场与基本盘

**Q1. 简单介绍一下这个项目。**

> 一句话，面向 MCN 商单业务的对话式智能助手——用户用自然语言提需求，大模型自主调工具，把「达人筛选、方案生成、审批流转、结案复盘、经验沉淀」整条闭环跑下来。  
> 技术上，LangGraph 做智能体编排，十九个工具；检索是 Milvus 向量库加 BM25 混合检索，两千零八十六块语料；后端 FastAPI 四十一个接口，前端 Vue3，PostgreSQL 十四张表。  
> 我做它是因为我之前在 MCN 做过达人和商务对接，痛点是第一手的：筛达人、估报价、查案例、跟进度全靠人在几张表里翻，**而且经验沉淀不下来，换个人接手重新踩一遍坑**。  
> 最关键的差异点是——**我给它配了一套独立评估体系**，一百零七道题跟语料解耦出题，检索和生成质量都实测过，指标和口径都能复现。

**旁注**：这是钩子题。**把最亮的点放最后一句**，主动引导面试官往「评测」追问。不要一上来铺技术细节——铺了就等于告诉他「我只有技术栈」。

**Q2. 这个项目是你一个人做的吗？团队里你负责哪块？**

> 从我这条线来说是全链路负责的——数据、检索、Agent、后端、前端到评测都是我做的。  
> 需求侧不是我自己拍脑袋：达人筛选和商单跟进的流程细节是跟商务、运营同事对齐出来的，比如「拒绝原因」「返点」「档期」这几个字段就是他们告诉我必须留痕的，后来才变成跟进工具的富化引导。  
> 中间经历过一次推倒重建——第一版是固定流水线的 RAG demo，多轮对话、工具调用、写回闭环全缺，判定不合格，重构成了现在的真 Agent 版本。  
> 时间上我给不了准确的工时数字，**我没做过实际计时**。但迭代节奏是清楚的：十二个可验收的阶段，每个阶段都有落盘日志和验收脚本。

**旁注**：**「没做过实际计时」要主动说**——这个项目的纪律就是不用无来源数字，面试里保持一致，面试官会因此更信任你其它数字。另外这题现在是**工作经历语境**，所以要主动提一句协作来源；如果写成「我一个人全包」反而浪费了工作经历最值钱的部分（协作与真实约束）。

**Q3. 用一句话说清它和「能聊天的 RAG demo」的区别。**

> 三条。  
> **第一，真 Agent。** 不是我写「先查 A 再查 B」的固定剧本，而是把十九个工具的签名和说明交给模型，由它自己决定调哪个、调几次、什么时候停。用户一句「顺便记个跟进」，我不用为这种组合意图写路由分支。  
> **第二，有写回闭环。** 对话里产生的方案、跟进、沉淀、审批全部落库、可追溯、可审计，不是聊完就没了——第一版栽的就是这个。  
> **第三，所有写库动作过闸门。** 外部数据进正式表要 AI 预审加人工双审；对话经验入库要两次确认、确认前零落库；商单主字段变更 Agent 无权直改，只能建申请走审批流。

**旁注**：这是**分水岭题**。答不出这三条，面试官会归到 demo 级。**把三条背成肌肉记忆**，而且要能展开——三条里任意一条都可能被继续追问。

**Q4. 最大的技术挑战是什么？**

> 检索层的「同构文档淹没」。  
> 现象是高相关文档被结构相似的文档挤出排名——美妆刊例表在向量召回里排第一，RRF 融合之后掉到第十五。根因是几十份结构几乎一样的在途跟踪单，靠数量优势主导了融合分数。  
> 修复过程中我还犯过一次错：去重最初放在融合**前**的两路列表上，污染了 RRF 的输入排名，结果命中率从零点六三三崩到零点三一六。后来定位到，把去重移到融合**后**，用「保序加溢出移队尾、不丢弃」的策略，恢复到零点七四。  
> 这个 bug 教我的比修好它更有价值：**组件在管线中的位置，比组件的参数影响大得多。**

**旁注**：**主动讲自己犯的错并给出教训**，是建立可信度最快的方式。但只讲**已经修好**的错，不要讲悬而未决的。

**Q5. 你说做了评测，为什么不直接用开源评测框架，要手工实现？**

> 因为我需要精确控制判分输入的完整性。  
> 开源框架默认会对上下文做裁剪，而裁剪会把支持某个论断的原文截掉，导致忠实度被低估——本来能推出结论的回答被判成编造。  
> 我手工实现的分段判分是把回答拆成「结论段」和「依据段」，各自跟完整上下文配对判分，再在论断级合并取均值。这样每个论断的判分过程**可审计**，我才能拿到失分明细做逐条归因——这是用框架拿不到的。  
> 当然代价是开发成本更高，这个取舍我认。

**旁注**：考点&#x662F;**「知不知道框架的边界」**。只说「框架不好用」是减分；说出「框架的哪个机制、在什么场景下产生什么偏差」是加分。

**Q6. 这个系统上线了吗？有真实用户在用吗？**

> 分两层说，别混。  
> **公司那侧**：它是内部系统，有真实同事在用，需求就是从商务和运营的日常流程里长出来的。（**这块你按实际情况补数字**：服务多少人、覆盖多少在途单、替掉了原来哪几个手工环节。）  
> **我本地这套复刻版**：没有用户，它是用来做技术自证和复现的——用合成数据、按同样的架构和评测方法搭的，我给你的所有指标和排查过程都在它上面可复现。  
> 至于系统性的用户实测——比如邀 5-8 人做任务式测试配可用性量表——我方案里设计了，但按优先级排在最后一阶段，**还没执行**。

**旁注**：这是**诚实性 + 口径题**。两层分开说是关键：含糊其辞容易被当成"只有 demo"；把复刻版说成生产系统，被追问「线上指标多少」又答不上。**分层回答既真实又显专业。**

**Q7. 如果让你把它做成商业产品，还缺什么？**

> 四块。**用户侧**——系统性的用户实测和线上埋点还没有；**工程侧**——CI、并发压测、监控告警，现在验收靠脚本手动跑；**合规侧**——达人数据脱敏我现在做了（手机号前三位后四位、微信号哈希），但真实商用还要过数据授权和平台协议；**效果侧**——工具调用的用例集还没建，这块是 Agent 行为质量的专项评估。  
> 另外有些功能是我**刻意不做**的：周报生成、档期日历、多 Agent 编排、结算引擎——因为跟核心闭环关系不大，做了就是铺摊子。

**旁注**：**主动说「刻意不做的部分」很加分**——它证明你有取舍判断，而不是「想到什么做什么」。这也是这个项目设计文档里明确的取舍纪律。

### O2. Round 2 · Agent 连环追问链（连答到底，不喘气）

**Q8. 你说 Agent 自主选工具，怎么保证它不乱调？**

> 四层约束。  
> **第一层是工具接口本身**——每个工具的 docstring 都写清「何时该调我」，这是模型唯一的判断依据，所以我把 docstring 当接口契约来写。  
> **第二层是步数上限**——`recursion_limit` 设成二十五兜底，实测设十二会在复杂连环调用时爆图递归错误。  
> **第三层是错误兜底**——工具执行异常会被转成文本回喂给模型，让它自己调整，不中断整轮对话。  
> **第四层是写操作闸门**——就算模型调了写工具，真正落库前还有确认卡或审批流。

**追问 Q8-1：如果模型就是要调一个不该调的工具呢？**

> 那就得看这个工具是读还是写。  
> **读操作**调错了，代价是浪费一次调用、回答质量下降——但不会污染数据，我接受这个风险。  
> **写操作**调错了，是数据事故。所以我在架构上就不给它直改的权限：商单主字段变更没有 UPDATE 工具，只有「建申请」的工具。**这不是靠提示词求模型别乱来，是靠工具集本身不提供这个能力。**

**旁注**：这是追问链的第一次施压。**关键词是「不是靠提示词，是靠工具集不提供这个能力」**——把不可靠的约束换成结构约束，这是工程思维的核心。


**追问 Q8-2：你说写操作过闸门，这个闸门是给谁看的？**

> 给**人**看的，不是给模型看的。
> 闸门的设计前提就是「不完全信任模型」。确认卡展示抽取结果让人核对，审批流把变更申请摊到人面前——人是最后一道防线。
> 举个实测的例子：导入数据的时候，Agent 预审抓出过一条预算负两万的脏数据判了 reject；但就算它判了 pass，管理员在暂存区还有一次逐条确认或驳回的机会。**两层独立把关，任何一层失效都还有另一层。**

**追问 Q8-3：如果用户说「确认了」，但模型没调入库工具呢？**

> **确实出现过这种波动，我承认。**
> 早期我把沉淀流设计成两步工具——先记录、再确认。结果模型出现过三种坏行为：跳过工具只做口头总结、一步到位不等确认、反问商单号打断流程。
> 我的修复是**把两步合并成一个原子工具**，把确认关口从工具层移到对话层，配上提示词硬约束。效果是从波动提升到**连续三轮验收稳定**。
> **但要百分之百确定，靠提示词是不够的。** 彻底方案是把待确认数据放进 LangGraph 的 state，用确定性分发判断——这个我记在待办里，路径是明确的。

**旁注**：这题是**最狠的一击**——它在测你是不是「嘴上说严谨」。**必须承认波动**，然后给出「结构方案 vs 提示词方案」的判断。说「我的模型百分之百听话」的人，面试官会立刻不信你其它话。

**追问 Q8-4：那你怎么知道它真的入库了？**

> **直接查数据库，不信模型的话。**
> 我的验收脚本里，断言是直接连 PostgreSQL 查表的——比如「messages 表真有新行」「deal_followup 表真有新行」，不是看模型返回什么文本。
> 这个习惯是被逼出来的：早期我确实靠模型的自然语言回复判断，后来发现有「说入库了但数据库没变」的情况。**验收断言必须落在真实存储上，不能落在模型的自我陈述上。**

**旁注**：这句「**不能落在模型的自我陈述上**」是整个 Agent 工程里最关键的一句话。能说出它，说明你真的踩过坑。

### O3. Round 3 · RAG 连环追问链

**Q9. 说说你的检索链路。**

> 完整链路六步：多路召回——Milvus 向量和 BM25 关键词两路并联，各路取候选池；然后元数据预过滤，按类目、平台、量级、粉丝区间筛；然后 RRF 倒数排名融合；然后文档类型先验加配额保底；然后文档级去重，每份文档最多留两块；最后送云端重排序模型精排，取出前五条进上下文。

**追问 Q9-1：RRF 为什么比「分数加权求和」好？**

> 因为**不同检索器的分数不可比**。向量的余弦相似度是零点几到一之间，BM25 的分数是没有上界的实数——直接加权求和，权重就得靠拍脑袋调，而且换个语料、换个 BM25 实现，这个权重就失效了。
> RRF 只用**排名**不用分数，公式是每个候选累加 `1/(k+rank)`。它把「两路都靠前」当成共识信号，天然免疫分数尺度问题。**这也是它能做成零调参的原因。**

**追问 Q9-2：你说去重放在融合之后，为什么？放在前面会怎么样？**

> 放在前面会**污染 RRF 的输入排名**。
> 去重的动作是「同一文档超出配额的第二块、第三块要处理掉」。如果我在融合前就把这些块从各路列表里删掉或移走，那各路列表的**原始排名序列就变了**——后面参与融合的就不是「向量真实召回的前二十名」，而是「被我修剪过的前二十名」。融合出来的分数自然就错了。
> 实测的后果很直接：正确文档整体沉底，那一组消融的命中率从零点六三三崩到零点三一六。

**追问 Q9-3：那你怎么发现应该放在后面的？**

> 三步。
> 第一步是**消融对照**——单独打开去重组件，指标反而崩了，说明这个组件本身有问题，不是「有没有用」的问题，是「放错位置」。
> 第二步是**打印各路的原始排名**，看到正确文档在向量路明明排第一，融合后却不见踪影，把怀疑范围锁定到融合前后的差异。
> 第三步是**块级追踪**定位到具体是哪一步把它的排名改掉了。
> 修复方案我没选「干脆不做去重」，而是改成在融合后做「保序加溢出移队尾」——**溢出的块不丢弃，只是移到候选池队尾，重排序那一步还能看到它。**既不破坏融合分数，又抑制了同构文档刷屏。

**旁注**：这题答完是这个追问链的高潮。**「不是删掉组件，是给它找对位置」**——体现的是归因而非逃避。

**追问 Q9-4：你怎么保证你的消融实验是可信的？**

> 三条纪律。
> **第一，同条件**——五组消融一次性跑在同一评测集、同一语料版本上，每次只开关一个组件，其余全部不变。
> **第二，必须出分层矩阵**，禁止只报总平均。因为总平均会掩盖弱项——多约束聚合层普遍偏低、精确查找层拉高总分，只看总数会误判管线健康。分层矩阵同时是行动指南：精确查找层低说明有结构性缺陷，语义改写层低说明语义匹配不足。
> **第三，任何参数改动都要重跑对照**，而且**不同语料上的结论不能横比**。

**追问 Q9-5：你的语义改写层为什么差？根因是什么？**

> **词汇鸿沟。** 用户的口语和文档的书面语之间没有共享词面。
> 用户问「这个达人现在什么身价」，文档里写的是「刊例报价」；用户问「那一单最后赚了没」，文档里写的是「结案数据、投入产出比」。
> 数据上很清楚：分层的五组消融里，语义改写层的命中率最高只有零点六五，而精确查找层是零点九三八，差了将近零点二九。
> 根因判断是**这一层的瓶颈不在排序，在查询理解**——排序模型再好，进来的查询向量本身就偏了。所以正确方向是查询改写，把口语归一成书面语，而不是继续调检索参数。

**追问 Q9-6：既然知道根因，为什么不现在就做查询改写？**

> 两个原因，一个是优先级，一个是**我不想在没有度量手段的时候动手**。
> 现在的评测集是有的，所以其实可以量化——但改写引入的是新的模型调用，会带来新的失败模式和延迟成本，我需要先想清改写的产出怎么评估：是只看这一层的命中率提升，还是看端到端回答质量。这两个口径可能给出不同结论。
> 所以我的判断是**先把度量定下来，再做改动**。不然改完只能靠「感觉更好了」，那不是工程。

**旁注**：这题在考**「你有没有自我约束」**。很多人会说「下一步就做」——但加一句「先定度量口径」立刻拉开层次。

### O4. Round 4 · 评测方法论深挖（差异化重点，会被重点问）

**Q10. 你怎么保证评测集不是「自证偏乐观」？**

> 三条纪律。
> **第一，先出题、后标注。** 题目由业务视角拟定——一个商单运营同事真实会问的问题，出题人不得先浏览语料原文再倒推题目。这一步是在防「照着语料抄问题」，那样检索只要做字面匹配就能得分。
> **第二，双向校验。** 每道题标完，反向检查题目措辞和相关文档的字面重合度，几乎完全重合的降级到低难度层或改写。
> **第三，解耦更新。** 语料变更不自动让评测集失效，只有某题的相关文档被删除或整份重写才修订那一道。评测集版本独立于语料版本演进，报告里必须同时注明两者版本号。

**追问 Q10-1：但你的语料和评测集本质上还是同源的啊，这怎么说？**

> **你说得对，这是一个真实的方法论风险，我主动交代。**
> 我的缓解方式是评测集**动态反查当前库**——语料一变，评测集跟着重建，不做一次性手工题库。这能防住「语料换了、评测集还是旧的」这类最严重的问题，但**确实防不住「出题人潜意识里知道语料里有什么」**。
> 要彻底解决，得引入外部标注者或者用真实用户日志出题。我目前做不到，所以我选择**把风险写在报告里，而不是假装它不存在**。

**旁注**：**这是全场最有含金量的一问**。承认 + 说明缓解手段 + 说清缓解的边界。**面试官问这题是想看你会不会 defend 自己的数据**——你越是坦然，他越信你的数字。

**Q11. faithfulness 零点九四五是怎么算出来的？**

> 判分模型从回答正文里抽取**事实性论断**，逐条判断能不能从检索到的上下文推出来，被支持的论断占比就是得分。
> 我的实现是**分段判分**：把回答拆成「结论段」和「依据段」，各自与**完整上下文**配对判分，再在论断级合并取均值。
> 为什么要分段？因为开源实现会把上下文裁剪后一起喂给判分模型，而裁剪会把支持某条论断的原文截掉，那条论断就被判成编造。**忠实度会被系统性低估**。手工实现让我能控制判分的输入完整性。

**追问 Q11-1：判分模型为什么要跟生成模型不同源？**

> **避免自我偏好。** 同一个模型给自己写的回答打分，倾向于认为「我写的就是对的」——尤其是它的输出风格和推理路径是自洽的，判分时会默认这种自洽就是正确。
> 所以我的生成走一个模型，判分走**另一家云服务商的模型**（qwen-plus 判 qwen3.8-flash），温度取零保证可复现。
> 这个原则在评测里是硬要求：**判分者和被评对象不能是同一个主体**。

**追问 Q11-2：你怎么知道零点九四五不是判分模型太宽松？**

> 三个交叉验证。
> **第一，判分温度取零 + 提示词给出抽取规则和输出格式约束**，减少随机性。
> **第二，我不看总分，看失分明细**——十九条未获支持的论断我全部做了二判加人工复核，逐条归因，不是只拿到一个数字就收工。
> **第三，还有一层完全不依赖判分模型的校验**——数值保真是代码确定性执行的，正则抽取回答引用块里的数值跟原文比对，这个百分之百没有判分模型参与。**两条独立路径互相印证。**

**追问 Q11-3：既然零点九四五已经不低了，为什么还要花时间做失分归因？**

> 因为**分数本身不是可执行的**。
> 「零点九四五」只能告诉我「还不够高」，但下一版该改什么？不知道。
> 归因之后我看清了：十九条失分里，真正超出检索依据的编造只有十条，而且**集中在归纳类问题上**——模型把在途跟踪单的字段当成已核实事实来复述；另有四条是我判分口径过严、四条是评测脚本自己的伪影（评估复现检索时的候选数跟生成链路不一致）。
> 这就把「零点九四五」变成了一句可以写进提示词的约束：**跟踪单的候选达人和需求描述，只能作参考性表述，不能当成已核实事实。**这是一个具体的、可验收的改进项。

**旁注**：**「把模糊分数变成可执行改进项」是这个项目评测部分最值钱的一句话。** 能说出它，说明你不是为了刷分做评测。

**Q12. 有没有指标没达标？为什么留着不改？**

> 有，**上下文精确率零点七三一，目标线是零点七五，临界未达标**。
> 归因是：上下文窗口限制在四千字符，多标注题目里相关文档的配额会被挤掉。
> **留着没改，是因为改口径很容易——我把窗口调大、或者把分母挑一挑，这个数就上去了。但那样报告就没有意义了。**
> 我的判断是：这个指标真实反映了当前窗口配置下的排序质量，它是**真实短板，不是错误**。所以我把它如实写在报告里，改进方向也写在报告里——扩大窗口和父块扩展的收益需要单独评估，那是下一轮的事。

**旁注**：这是**诚信测试题**。报一个未达标指标比报五个达标指标更能建立信任。**关键词是「改口径很容易，但那样报告就没意义了」。**

### O5. Round 5 · 工程与取舍

**Q13. 为什么坚持「Service 层唯一写库」？这不是过度设计吗？**

> 不是过度设计，是**防腐**。
> 这套系统里写库的地方天然很多——Agent 工具会写、REST 接口会写、导入脚本会写、运维脚本也会写。如果没有单一入口，ID 生成、状态机校验、留痕逻辑就会在四个地方各写一遍，然后慢慢长歪。
> 集中到 Service 层之后，好处有两个：**改规则只改一处**，加一条状态机的防呆不用去改四个地方；**审计时能一眼断定「数据是谁在什么规则下写的」**。
> 代价是工具函数和 API 都不能直接写库，要绕一层——但这一层的成本是可控的，收益是长期的。

**追问 Q13-1：那你怎么保证别人不绕过 Service 直接写库？**

> **诚实说：目前靠的是约定和代码组织，不是硬约束。**
> 我实际做到的：所有工具函数和 API 路由的写操作都调 Service，我自己的代码没有绕过。但技术上没有任何东西能阻止一个新同事直接拿连接对象执行 UPDATE。
> 要真正锁死，可以加两层——**静态检查**扫所有直接操作数据库的调用点，只允许白名单里的 Service 文件；**CI 门禁**在合并前拦住。这两条我都记在待办里，但**没做之前我不会说它已经做了**。

**旁注**：这题是**深挖一致性**。说「我保证没人能绕过」是吹牛；说「靠约定 + 我计划加 CI 检查」是可信。

**Q14. 十四张表是不是有点多？**

> 不多，都是不同生命周期的实体。
> 原来的六张是业务主数据：达人、商单、品牌、跟进流水，加上检索用的父子块两张。
> 新增的八张分三类：**会话类**——会话和消息，支撑多轮对话持久化；**审批类**——方案加方案版本表、商单变更申请表，都是「申请 + 版本痕」的形态；**沉淀类**——特质表、导入暂存表、用户表。
> 判断标准很简单：**有没有独立的生命周期、有没有独立的读写规则。**方案和方案版本必须分表，因为一版方案要留痕；会话和消息必须分表，因为一个会话多条消息。

**追问 Q14-1：为什么用 PostgreSQL 不用 MongoDB？**

> 因为核心数据的形态是**强关系加事务**。
> 商单、达人、跟进流水之间是多对多关系，状态流转要做校验——「草稿不能直接批准」这类防呆，就是状态机约束，落在关系库上是自然的。而且变更审批要求原子写回加留痕，需要事务。
> MongoDB 的优势在结构自由和水平扩展，我这个场景的数据结构是**收敛的、需要约束的**，用文档库反而把约束丢了。
> 向量这部分我用 Milvus，不跟关系库混。

**追问 Q14-2：这套东西 QPS 能到多少？**

> **没做过并发压测，我给不了数字。**
> 但从架构上判断，瓶颈不会在应用层——FastAPI 异步、检索是本地向量库加云端重排、数据库是本机。**真正的瓶颈是 LLM 服务端的配额**，多工具链的问题要串行好几次模型调用，这个是主要耗时。
> 要给出真实数字，得先压测后端接口拿到基线，再单独测模型调用的并发上限。**这两块我都没做，所以我不编。**

**旁注**：**「我不编」三个字是这题的答案。** 面试官问 QPS 往往不是要数字，是要看你会不会编。

### O6. Round 6 · 压力与质疑（最难的一轮）

**Q15. 我觉得你这个项目就是个套壳的 RAG，没多少技术含量。**

> 我理解这个判断的依据——形态上确实是「检索加生成」。
> 所以我想给三条可验证的区别，您可以顺着任一条追我。
> **第一，工具集是我设计的，不是框架给的。** 十九个工具的粒度、每个 docstring 的措辞、哪些能力只读、哪些写操作要过闸门，这些设计直接决定了智能体的行为上限。我举过一个实例：早期检索工具不支持按达人名字查，模型想找个具体的人时会换类目盲扫十几轮；加了名字模糊匹配之后，同类问题两步收敛。**工具接口设计的权重，比换个更大的模型高得多。**
> **第二，检索管线我做了组件级消融。** 五个组件每个的贡献都能隔离出来，还定位过一个「组件放错位置」的真实 bug——去重放在融合前会让命中率从零点六三三崩到零点三一六。
> **第三，评测体系是自建的。** 一百零七题、与语料解耦、判分模型不同源。
> 如果这三条里有哪条您觉得还是「套壳」，请继续追，我们再往深聊一层。

**旁注**：**不要辩解，给可验证的抓手，然后邀请继续追问。**「请继续追」这个动作本身就在展示你有底气。

**Q16. 你的指标是不是自己调参数调出来的？**

> 不是，而且**消融实验的目的恰恰是排除这个质疑**。
> 调参是「找一个让总分最好看的配置」；消融是「每次只开关一个组件，看它单独贡献多少」——这两种操作的方向是相反的。
> 另外有一个反证：**我报了三个未达标或短板项**——上下文精确率未达标、语义改写层是短板、重排序对归纳类问题增益有限。如果目标是让分数好看，这三项我应该藏起来或者换口径。**我把它们留在报告里，是因为报告的作用是定位问题，不是宣传。**

**Q17. 数据是你自己造的，那这个评测还有意义吗？**

> **数据是三层，我分开说。**
> **达人库一万四千多条是真实数据**——正式 Excel 双 sheet 两万多行清洗重灌的，包含脱敏、多子表纵向拼接的位置感知解析、分成编码的语义化。
> **商单和甲方是按真实业务规则构造的**——预算对齐达人单价上限、CPM 锚定星图行业区间、平台间有差异。涉密的真实商单不可能外流，用真实规则仿真是这个场景下的标准做法。
> **案例语料是由库内效果数据确定性渲染的**，不是模型生成的——所以文档和台账天然一致，引用可以验证。
> 至于评测的意义：**评测的是检索和生成这条链路的能力，只要语料不是随机噪声、评测集跟语料解耦、标注有纪律，这个结论就是有效的。**但同时我也承认：同源生成存在偏乐观风险，这一点我写在报告里。

**旁注**：**三层分开说，并主动提「偏乐观风险」**。含糊其辞地讲「数据都是真的」会被追死。

**Q18. 你说你懂 MCN，那你觉得这个系统能替代商务吗？**

> **不能，也不该往这个方向做。**
> 商务的核心价值在谈判、关系维护、对甲方意图的判断——这些是人和人之间的事，系统替代不了。
> 这个系统的定位是**把重复劳动和记忆负担接过来**：从几张表里翻达人、翻历史报价、翻结案效果，这些原来是耗时的机械劳动；同时把散落在微信聊天记录里的谈判经验变成可检索的资产——**原来人走了经验就没了，现在它留在库里**。
> 所以它更像副驾驶。如果我说它能替代商务，那反而是我没理解这个业务。
